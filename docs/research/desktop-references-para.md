# 데스크톱 문서·지식 관리 레퍼런스와 PARA 효용성 검토

- 조사일: 2026-11-02, Asia/Seoul
- 배경: 사용자는 첫 세 시안이 원하는 느낌이 아니라고 피드백했고, 관련 서비스의 화면과 운영 방식을 먼저 검토한 뒤 PARA의 효용성도 비교하도록 요청했다.
- 근거 수준: 공식 제품·도움말, 공식 공개 화면의 브라우저 시각 검토, 제한된 이용자 경험담. 계정 생성·로그인·자료 업로드·실제 제품 작업은 하지 않았다. 공개 이미지로 실제 사용 속도·검색 품질·장기 유지 부담을 검증했다고 보지 않는다.
- 관련: [PRD](../product/prd.md), [디자인 검토](../design/desktop.md), [기존 유사 제품 비교](alternatives.md).

## 검토 결론 — 제안이며 채택 결정이 아님

SiloLink의 다음 설계는 기존 CLI 메뉴를 화면으로 옮기는 구성을 출발점으로 고정하지 않는다. 사용자가 하는 일과 지식을 다시 사용하는 맥락을 먼저 정리한다. 아래 서비스의 색과 외곽 배치뿐 아니라 정보 단위·원문 읽기·관계 표시·일상으로 돌아오는 방식을 비교한다.

현재 적합성 판단은 **Capacities의 연결된 지식 허브, Craft의 문서 읽기·자료 탐색, Google의 자료 기반 채팅**을 우선 참고하고, 개발 업무 연결은 Linear, 여러 근거를 펼치는 작업은 Heptabase, 로컬 원문과 다중 보기는 Obsidian에서 검토하는 것이다. 이 조합의 효용은 SiloLink에 대한 설계 추론이며 서비스 도입·성능 우열·사용자 선호가 입증됐다는 뜻은 아니다.

PARA는 현재 목표·지속 책임·재사용할 자료·비활성 정보를 구별하는 데 도움이 될 수 있다. SiloLink에는 **선택 가능한 분류·연결·보기 방식**으로 적용하는 안을 우선 제안한다. 모든 저장소를 동일한 네 폴더로 다시 짜는 정책이나, 모든 AI 발화를 자동 분류하는 동작은 확정하지 않는다.

### 실제 공개 화면에서 관찰한 점

- Capacities의 개념 노트 화면은 본문·목차/관련 개체·다른 자료를 함께 보여준다. 프로젝트 허브는 상태·일정·Area, 작업, 관련 링크, 일일 노트의 역참조를 한 맥락에서 읽게 한다. 같은 3분할이어도 ‘폴더/파일/본문’과 전달하는 의미가 다르다.
- Craft의 Collection 화면은 같은 항목에 속성과 본문이 있고, 자료에 맞춰 표와 갤러리를 바꾸는 방식을 보여준다. SiloLink의 기술 자료는 무조건 사진 카드보다 제목·주제·출처·관련 프로젝트가 중요한 경우가 많다.
- Heptabase의 공개 화면은 자료를 묶고 관계를 그리는 화면과 상세 읽기를 동시에 유지한다. SiloLink에는 전역 관계 그래프를 장식으로 넣기보다 실제로 비교 중인 근거를 펼치는 용도로 검토할 가치가 있다.
- Notion 화면은 하나의 페이지에 설명·연결된 업무·요약을 구성한다. Linear 화면은 업무 경로와 긴 명세의 본문에 집중한다. 이 둘은 작업의 전체 맥락과 문서 집중 보기의 서로 다른 참고다.

## PARA는 무엇을 정리하는가

Tiago Forte의 [PARA 원문](https://fortelabs.com/blog/para/)은 정보를 주제 이름만으로 나누기보다 현재 목표와 활용 가능성에 맞춰 정리하는 방식을 설명한다. 엄밀히는 기록의 문장 작성법이나 학습 판정법보다 정보 조직 방법이다.

| 구분 | 원래 의미 요약 | SiloLink 맥락의 예시 — 적용 제안 |
| --- | --- | --- |
| Projects | 지금 추진하는 목표가 있는 단기적 노력 | ‘데스크톱 첫 사용 흐름을 사용자 테스트로 확인하기’, ‘공통 규칙 v1 정리하기’ |
| Areas | 지속해서 책임지고 기준을 유지할 영역 | AI 활용 개선, 문서 품질, 프로젝트 운영, 개발 규칙 유지 |
| Resources | 관심·학습·향후 활용을 위한 주제와 자료 | Rust 소유권 설명, SQLite 조사, 공식 기술 문서·논문·커뮤니티 의견 |
| Archives | 앞선 범주 중 현재 비활성인 정보 | 끝나거나 보류한 목표, 대체된 조사·예전 결정의 근거 |

원문은 네 상위 폴더의 형태도 제시한다. 이 문서의 링크·보기 중심 적용안은 원문의 파일 이동 구조를 그대로 구현하는 것이 아니라 SiloLink에 맞춘 변형이다.

Forte의 [AI 시대와 PARA 글](https://fortelabs.com/blog/why-para-is-the-key-to-the-ai-era/)은 목표에 맞게 묶은 자료를 AI 문맥으로 제공하는 가치를 주장한다. 저자의 경험·견해이며 SiloLink에서 요청 품질·검색 정확도·업무 시간 개선이 실증됐다는 근거는 아니다.

## 효용과 한계 — SiloLink에 대한 추론

| 사용자 문제 | PARA가 도움을 줄 수 있는 부분 | 별도로 필요한 능력 |
| --- | --- | --- |
| 여러 프로젝트에서 같은 내용을 다시 조사 | 재사용할 자료를 Resources로 모으고 여러 목표에서 연결 | 내용 검색·중복 후보·버전/조건 비교·출처 유지 |
| 공통·로컬 규칙 운영 | 지속 관리할 영역을 Areas로 드러내고 관련 프로젝트 연결 | 상속·예외·충돌·실제 적용·복구 정책 |
| 끝난 일과 진행 중인 일이 섞임 | 목표의 활성/보류/완료를 구별하고 비활성 자료를 일상 보기에서 줄임 | 실제 완료 판단·사용자 테스트·진행 이력 |
| AI에게 어떤 자료를 줄지 불분명 | 현재 목표에 관계된 문맥 묶음을 선택하기 쉬움 | 선택 범위·권한·원문 revision·토큰 범위·상충하는 자료 처리 |
| 모호한 요청·파편화된 이해 | 관련 학습 자료와 작업을 연결하는 보조 역할 | 원문 근거 분석·의미 후보·사용자 수정·학습 가이드. 분류로 이해 수준을 판정할 수 없음 |
| AI가 매번 다른 작업 시간을 제시 | 끝나는 목표와 지속 책임을 구별하는 출발점 | 실제 시간·작업 단위·병렬 수행·조건·유사 실적. PARA만으로 예상 시간을 보정할 수 없음 |

효과는 가설이다. ‘PARA를 썼으니 잘 정리됐다’가 아니라 필요한 근거를 다시 찾아 실제 작업에 재사용할 수 있는지로 판단해야 한다.

### 저장소와 PARA Project를 구별해야 하는 이유

SiloLink의 `projectId`는 현재 저장소/프로젝트 원본의 귀속을 보존한다. PARA Project는 끝나는 목표다. 둘을 같은 것으로 강제하면 제품 하나의 장기 운영을 끝나지 않는 Project로 만들거나, 하나의 목표에 필요한 여러 저장소를 나누게 된다.

- 한 저장소에는 ‘CLI 이식’, ‘데스크톱 첫 버전’, ‘규칙 개편’ 같은 여러 목표가 생길 수 있다.
- 하나의 ‘공통 규칙 개편’ 목표는 여러 저장소에 걸칠 수 있다.
- 저장소를 유지하면서 특정 목표만 완료·보류할 수 있어야 한다.
- ‘데스크톱 만들기’라는 지속 제품 운영과 ‘첫 사용자 테스트를 마친다’라는 완료 조건을 구별한다.

이는 개념 모델 제안이다. 새 ID·DB 테이블·프로젝트 정책을 이번 조사에서 구현하거나 확정하지 않는다.

### 원본 위치와 분류를 분리하는 안

[Capacities의 공식 PARA 가이드](https://docs.capacities.io/reference/use-cases/para-in-capacities)는 객체·링크·속성과 상태 필터로 PARA를 적용하는 예시를 제공한다. 하나의 자료를 여러 프로젝트에서 연결하고, 보관을 이동 대신 상태/보기로 다루는 방식이다. 이 사례는 네 폴더 외의 실제 구현 참고가 되지만 SiloLink의 원본 파일·귀속·동기화 요구까지 해결해 주지는 않는다.

SiloLink에는 다음을 제안한다.

1. 저장소의 기존 Markdown·출처·경로·revision을 보존하고, 그 위에서 목표·영역·주제를 연결한다. PARA 때문에 모든 파일의 위치를 바꾸지 않는다.
2. 같은 SQLite 조사는 한 원본을 여러 목표에서 참조한다. 목표 하나가 완료돼도 다른 목표가 사용하는 지식은 함께 숨기거나 폐기하지 않는다.
3. 분류와 보관은 문맥에 따라 다르게 적용할 수 있어야 한다. 전역 숨김·검색 제외·파일 삭제를 같은 행동으로 취급하지 않는다.
4. 미분류 상태를 허용한다. 모든 AI 메시지에 즉시 분류를 요구하지 않고, 재사용할 만한 조사·개념·결정 후보를 사용자가 검토할 수 있게 한다.
5. 원문, AI가 추출한 후보, 사용자가 검토한 문서를 구별한다. 자료가 모였다는 사실만으로 공식 문서나 확정 규칙이 되지 않는다.
6. 실제 중복 제거·통합·재작성·삭제는 기존 변경안 검사·적용·복구 경로로 수행한다. 논리적 분류나 아카이브 보기를 만든 것을 실제 문서 정리 완료로 표시하지 않는다.

### 현재 문서를 사용한 적용 예시

| 원본 | 연결할 맥락의 예시 | 물리적 변경 여부 |
| --- | --- | --- |
| `docs/product/prd.md` | 데스크톱 목표의 요구 근거, 제품 운영 영역 | 이번 조사에서는 변경 구조·이동 없음 |
| `docs/development/cli.md` | 코어 호환·문서 변경/복구를 지속 관리하는 영역 | 계약 원문 위치 보존 |
| `docs/research/basic-memory.md` | 재사용할 문서 관리 조사, 데스크톱 설계 목표의 참고 | 자료를 여러 목표에서 연결하는 후보 |
| 이 조사 문서 | PARA·문서/지식 관리 UI 자료, 새 정보 구조 검토 목표의 근거 | 조사 문서로 추가하며 PARA 분류 DB는 생성하지 않음 |

이 표는 문서 전체를 반드시 단일 PARA 칸에 넣겠다는 뜻이 아니다. 필요한 경우 특정 결정이나 절을 원문 참조로 연결하는 방식도 검토한다.

## 이용자 경험과 상반된 신호

다음은 개별 경험담이며 대표 표본·우수성 증명·결함 재현이 아니다.

- [Obsidian 포럼의 작업/노트/저널 구분 논의](https://forum.obsidian.md/t/how-do-you-manage-notes-vs-tasks-projects-vs-journal-entries/51884): 한 저장 공간 안에서 경로로 검색 범위를 줄이는 사례, PARA에 저널과 자체 노트를 더해 맞춘 사례가 있다. 개인의 실제 찾는 방식에 맞게 조정할 여지를 보여준다.
- [PKMS 이용자들의 시스템 공유](https://www.reddit.com/r/PKMS/comments/1ho8b1u/can_you_show_me_your_system_of_your_personal/): 앱에 따라 PARA를 폴더·태그로 달리 쓰거나 필요한 곳에만 생성하는 경험이 있다. 과한 시스템 구성에 시간을 쓰고 실제로 사용하지 못했다는 경험도 나온다.
- [개발자의 PKM 구성 경험](https://dev.to/gantengx/the-pkm-setup-i-settled-on-after-many-iterations-6pa): Area/Resource를 합쳐 쓰고, 프로젝트가 끝나도 남아야 할 지식을 별도로 연결하며, 과도한 메타데이터·역링크 유지 부담을 설명한다. 해당 글의 PARA 해석을 원래 정의의 대체 근거로 쓰지는 않는다.

따라서 ‘분류하면 다 좋아진다’와 ‘링크만 많으면 해결된다’ 모두 검증 없이 채택하지 않는다. 사용자에게 분류와 연결을 고칠 수 있는 수단을 주고, 유지하는 데 드는 수고를 관찰한다.

## 다음 정보 구조와 화면 검토의 기준

다음은 새 시안을 만들기 전 검토할 질문이며 화면 구성 확정안이 아니다.

- 무엇을 관리하는가: 파일뿐 아니라 원문 기록·조사·개념·결정·규칙·작업을 구별할 필요가 있는가. 사용자에게 처음부터 유형 설계를 요구하지 않는가.
- 무엇을 먼저 보는가: 현재 목표, 최근 이어가던 사고, 재사용할 자료, 일간/주간 회고 중 상황에 맞게 시작할 수 있는가.
- 어디서 활용하는가: 한 자료를 여러 프로젝트에 연결하고 어떤 조건이 다른지 비교할 수 있는가.
- 어떻게 읽고 질문하는가: 내용에 집중하면서 관련 근거를 함께 보거나 필요할 때 펼치고, 선택한 자료로 추가 질문을 이어갈 수 있는가.
- 어떻게 정리하는가: 보기·분류·판단 수정과 실제 파일 변경을 구별하고, 실제 변경 전에는 구체적인 전후 내용과 영향을 확인하는가.

사용자 검토에는 Capacities형 허브·Craft형 문서 공간·Heptabase형 사고 공간의 공개 화면을 먼저 제시한다. 이전 세 시안과 ‘초기 6화면·공통 후보 22종’을 새 설계의 고정 입력으로 삼지 않는다. 관리할 정보의 단위와 사용자 동선을 정한 뒤 공통 모듈 범위를 다시 산정한다. 공통 Rust 코어 재사용은 그대로 유지한다.

## 효용을 확인할 작은 비교

새 기능을 구현하기 전 실제 문서 사례에서 다음을 비교할 수 있다. 순서나 정해진 점수·완료 시간을 강제하지 않는다.

1. 기존 폴더/검색 방식과 연결·보기 방식에서 같은 SQLite 근거를 두 저장소의 작업에 다시 사용하는 과정을 비교한다.
2. 지속 관리할 규칙과 단기 개편 목표를 함께 보면서 로컬 예외를 보존할 수 있는지 확인한다.
3. 완료한 목표를 보관한 뒤에도 유효한 자료와 결정 근거를 다시 찾을 수 있는지 확인한다.
4. 미분류 상태로 시작해도 다음 작업을 할 수 있고, 잘못 분류한 항목을 고치는 부담이 적은지 확인한다.

관찰할 것은 필요한 자료까지의 찾기 과정, 원문·판단 상태의 이해, 자료 재사용 여부, 분류/연결을 고치는 수고다. 개선률·시간 절감·AI 분석 정확도는 아직 측정하지 않았다.
