# SiloLink를 CLI로만 제공할 것인가

- 작성일: 2026-11-01, Asia/Seoul
- 질문: 우리 서비스를 CLI로만 제공하는 것이 긍정적인가?
- 상태: 이전 잠정 권고. 후속 사용자 설명으로 제품 방향을 수정했으며 아래 안내를 참고한다.
- 근거: [프로젝트 인계 맥락](../context/silolink/CONTEXT.md), [CLI와 MCP 리서치](2026-11-01-cli-and-mcp.md), 아래 공식 저장소.
- 확인 범위: 기존 의도와 공개 문서를 대조했다. 사용자 인터뷰·제품 체험·시제품 구현은 수행하지 않았다.

## 후속 제품 방향에 따른 수정

2026-11-01 후속 대화에서 사용자는 CLI를 기반으로 여러 LLM용 플러그인과 데스크톱을 구성하고, 데스크톱 안에서 채팅·문서·작업 운영을 통합 관리하려는 목표를 명시했다. 이에 따라 데스크톱의 관리 경험도 초기 검증 범위에 포함하도록 권고를 수정한다. 아래 본문은 이전 가정에서의 검토 이력으로 보존하며, 현재 방향은 [CLI·플러그인·데스크톱 제품 방향](../product/2026-11-01-cli-plugin-desktop.md)을 따른다. 첫 구현 범위와 기술 스택은 아직 확정하지 않았다.

## 1. 기존 권고

**현재 구상에서는 첫 검증 버전을 CLI로만 제공하는 것은 긍정적이다. 장기적으로도 CLI만 제공할지는 실제 읽기·검토·공유 흐름을 확인한 뒤 결정하는 것이 적절하다.**

우선 가정은 사용자가 개발자이며, 평소 쓰는 에이전트와 편집기 안에서 프로젝트 기록을 저장하고 다음 작업에 재사용한다는 것이다. 사용자 대상과 사업 목적은 아직 확정되지 않았으므로 이 가정이 바뀌면 권고도 달라진다.

이 조건에서 자체 데스크톱 앱을 먼저 만들기보다 CLI와 기존 편집기로 핵심 흐름을 검증할 수 있다. 읽기와 비교에 반복적인 불편이 드러나면 정적 보고서나 작은 로컬 뷰어부터 보완한다. 처음부터 데스크톱·CLI·MCP를 모두 만드는 것은 검증 범위를 넓힌다.

다만 “CLI만 배포한다”와 “사람도 모든 일을 터미널에서 한다”는 다른 선택이다. SiloLink는 CLI로 배포하더라도 Markdown 파일을 기존 편집기에서 읽고 수정하게 할 수 있다. 또한 CLI라는 배포 형식만으로 로컬 저장·무서버·무료 운영이 정해지지는 않는다.

## 2. 우리 사용 흐름과의 적합성

기존 맥락에는 외부 코딩 프로젝트에서 기록을 저장·검색하는 흐름과, 사람이 리서치를 읽고 검토·공유하는 흐름이 함께 있다. 아래 평가는 이 요구를 기준으로 한 설계 판단이며 사용성 실험 결과는 아니다.

| 사용 흐름 | CLI의 적합성 | 필요한 보완 |
| --- | --- | --- |
| 프로젝트를 연결하고 기록을 저장 | 높을 것으로 예상 | 프로젝트 식별, 출처·시각, 중복 저장 방지 |
| 다음 에이전트 작업에서 과거 판단을 검색·재사용 | 높을 것으로 예상 | 제한된 검색 결과, 근거 위치, 안정적인 식별자 |
| 정형 리서치·브레인스토밍 문서 작성 | 기존 편집기와 결합하면 가능 | 템플릿, 필수 정보 확인, 외부 수정 반영 |
| 여러 조사 결과와 출처를 나란히 비교 | 터미널 출력만으로는 마찰 가능 | 편집기 활용 후 필요하면 비교 화면 검토 |
| 추천 문서의 연결 이유를 확인·수정 | 단순 목록은 가능, 탐색이 복잡해지면 검증 필요 | 추천 근거와 사람이 연결을 고칠 경로 |
| 기술 정리서 공유 | 산출물 형식에 따라 가능 | 수신자가 SiloLink를 설치하지 않아도 읽을 파일 |
| 비개발자와 공동 편집·검토 | CLI만으로 충분하다고 보기 어려움 | 대상 사용자가 확정되면 별도 검증 |

CLI에서 문서를 내보내는 방식도 가능하므로 공유를 위해 전용 앱이 반드시 필요한 것은 아니다. 반대로 사람의 읽기·검토 부담이 크다면 명령 실행 효율만 높여서는 제품 경험이 충분해지지 않는다.

## 3. 긍정적인 이유와 남는 비용

**검증 대상을 좁힐 수 있다.** 먼저 확인할 질문은 “저장한 리서치가 다음 작업에서 다시 쓰이는가?”다. 자체 창·탐색 UI·다중 에이전트 실행 관리 없이도 이 흐름을 시험할 수 있다.

**이미 있는 작업 환경을 활용할 수 있다.** 사용자는 에이전트에 기록 저장·검색을 요청하고, 직접 읽을 때는 평소 쓰는 편집기를 열 수 있다. CLI 명령을 매번 사람이 외울 필요가 없는 흐름도 설계할 수 있다. 다만 해당 에이전트의 셸 접근과 작업 지침이 실제로 작동하는지는 확인해야 한다.

**후속 제공 방식을 열어 둘 수 있다.** 기록 검증·저장·검색을 공통 기능으로 두고 CLI를 얇게 만들면, 후속 뷰어나 MCP에서 재사용할 여지가 있다. 실제 유지보수 절감은 경계와 구현에 달려 있으며 보장된 효과는 아니다.

줄어드는 것은 주로 전용 UI의 초기 구현 범위다. 다음 비용은 여전히 남는다.

- 설치·업데이트·OS별 경로와 문자 인코딩 지원.
- 프로젝트·워크트리 구분, 동시 수정, 원문 보존과 색인 일관성.
- 검색 품질, 오류 복구, 출처와 판단 상태 관리.
- 외부 모델을 사용할 경우 인증·요금·취소·데이터 전달 관리.
- 사용자가 기능을 발견하고 첫 기록을 재사용하기까지의 안내.

따라서 “CLI니까 개발·운영비가 거의 없다”거나 “MCP 대비 토큰 절감이 곧 우리 제품의 비용 절감이다”라고 계산하면 안 된다.

## 4. CLI만으로도 사람이 쓰기 좋은가: 공식 사례

Basic Memory는 같은 Markdown 파일을 사람의 기존 편집기와 AI가 함께 사용하는 구조를 설명하고 CLI 명령도 제공한다. 이는 전용 편집기를 직접 만들지 않는 접근의 참고 사례다. **Basic Memory 전체가 CLI 전용 제품이라는 뜻은 아니며**, SiloLink와의 적합성이나 우위는 체험하지 않았다. [Basic Memory 공식 README](https://github.com/basicmachines-co/basic-memory)

Playwright CLI는 에이전트의 CLI 사용을 권장하면서도 `playwright-cli show`로 사람이 진행 상태를 보고 개입하는 시각적 대시보드를 제공한다. CLI 중심 실행과 사람을 위한 화면은 함께 설계할 수 있다는 사례다. SiloLink에도 같은 화면이 필요하다는 증거는 아니다. [Playwright CLI Monitoring](https://github.com/microsoft/playwright-cli#monitoring)

**해석:** SiloLink에서 CLI의 장점을 취하기 위해 사람의 화면까지 없앨 필요는 없다. 먼저 기존 편집기로 충분한지 확인하고, 부족한 경험만 추가하는 쪽이 현재 단계에 맞다.

## 5. 선택지 비교

아래 비용·마찰 평가는 측정값이 아닌 상대적 예상이다.

| 선택지 | 얻는 것 | 부담·실패 가능성 | 현재 판단 |
| --- | --- | --- | --- |
| 현재 `docs/`와 편집기·검색을 계속 사용 | 추가 제품 개발 없이 기록 방식부터 검증 | 기록 간 재사용이 수동이며 프로젝트가 늘면 관리 부담 가능 | 비교 기준으로 유지. 지금 충분하면 개발 보류도 가능 |
| CLI+기존 편집기 | 에이전트의 저장·검색 흐름에 집중, 전용 UI 범위 축소 | 설치·탐색·프로젝트 설정과 편집기 간 이동 부담 | 첫 검증 버전으로 권고 |
| CLI+정적 보고서 또는 작은 로컬 뷰어 | 읽기·출처 확인·비교를 보완 | 추가 렌더링·뷰어 유지보수, 동적 편집은 별도 문제 | 실제 읽기 불편이 확인될 때 검토 |
| 전용 데스크톱 앱 중심 | 조사·검토·프로젝트 탐색을 한 공간에 묶을 수 있음 | UI·패키징·상태 동기화 범위 증가, 핵심 재사용 가치 검증 지연 가능 | 통합 작업 공간 수요가 확인될 때 재검토 |

가장 큰 제품 위험은 터미널 사용성보다 **기존 문서 폴더와 검색, 유사 도구에 비해 추가할 가치가 무엇인가**다. CLI 제공 자체는 차별화 근거가 되지 않는다. 설치와 기록 규칙 유지에 드는 수고보다 프로젝트 맥락 재사용의 이익이 커야 한다. 이 점은 현재 미검증이다.

## 6. 첫 검증 버전의 제안 범위

다음은 구현 요청이 아니라 후속 실험의 범위 제안이다.

1. 프로젝트 연결과 기록 저장: 본문·출처·작성 시각·제안/결정 상태를 남긴다.
2. 기록 검색과 근거 읽기: 다음 작업에 필요한 문서나 부분을 되찾는다.
3. 일반 파일로 열기·전달: 기존 편집기에서 검토하고 수신자는 앱 설치 없이 읽는다.
4. 에이전트 하나의 작업 지침: 저장 시점과 검색·검증 절차를 설명한다.

에이전트 실행을 모두 관리하는 런처, 모든 대화 자동 수집, 별도 클라우드 동기화, 다중 사용자 협업, 본격적인 그래프 화면은 이 실험의 필수 범위로 넣지 않는 것을 제안한다. 제품 전체에서 영구 제외한다는 결정은 아니다.

### 관찰 가능한 완료 기준

| 확인할 가치 | 완료 판단에 사용할 관찰 |
| --- | --- |
| 다음 작업에서 기록 재사용 | 새 세션에서 과거 문서를 찾고 그 근거를 연결해 작업을 이어 감 |
| 프로젝트 경계 | 다른 프로젝트를 대상으로 저장하려는 경우 명시적 확인 또는 오류로 드러남 |
| 기록 무결성 | 재실행으로 중복·원문 유실이 생기지 않고, 외부 편집 결과를 다시 조회할 수 있음 |
| 사람의 검토 | 기존 편집기에서 출처와 제안/결정을 구별하고 필요한 수정을 할 수 있음 |
| 공유 | 수신자가 SiloLink 없이 본문과 근거 링크를 읽을 수 있음 |
| 기존 방식 대비 가치 | 같은 실제 작업을 `docs/`+검색으로도 해 보고 탐색·복구 수고와 결과 품질을 비교함 |

합격 기준과 허용 시간은 실제 작업을 고른 뒤 정한다. 지금 임의의 절감률·유료 수요를 가정하지 않는다. 반복 사용에도 CLI만으로 검토·공유가 충분하고 재사용 가치가 확인되면 CLI 단독 제공을 계속할 근거가 된다. 읽기·검토에서 반복적으로 막히면 그 지점부터 보완한다.

## 7. 권고가 달라지는 조건과 남은 결정

- **본인 또는 개발자 중심의 개인 생산성**이 우선이면 CLI 단독 시작의 타당성이 높다.
- **비개발자를 포함한 리서치·검토 공간**이 우선이면 화면과 협업 흐름을 더 일찍 검증해야 한다.
- **셸이 없는 외부 호스트 연결**이 필수이면 MCP 등 그 호스트의 연결 방식을 검토해야 한다.
- **기존 편집기와 문서만으로 충분**하면 자체 CLI를 만들 필요성부터 다시 평가한다.

주요 사용자, 개인 도구와 외부 판매 제품 중 우선 목적, 기존 편집기를 사용하는 경험의 수용 여부는 사용자가 결정할 사항이다. 현재 문서는 개발자 개인 사용을 가정한 잠정 권고이며, 사용자 답변이나 구현 약속으로 기록하지 않는다.
