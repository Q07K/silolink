# SiloLink 제품 방향: CLI·플러그인·데스크톱

- 작성일: 2026-11-01, Asia/Seoul
- 목적: 사용자와의 대화에서 구체화한 제품 목표와 이를 위한 설계 제안을 기록한다.
- 상태: 제품 목표 확인. 세부 규격·기술 스택·구현 순서는 미확정.
- 구분: 아래의 사용자 목표와 설계 제안은 구별한다. 문서 저장 요청을 모든 설계 제안의 확정이나 구현 착수로 해석하지 않는다.

## 후속 인터뷰

이후 대화에서 사용자 대상, 자동 분석·학습 지원, 근거 기반 조사, 프로젝트 간 규칙 관리, 실적 기반 플래닝 요구가 구체화됐다. 최신 요구와 사용자가 정정한 범용 지원 원칙은 [제품 인터뷰 정리](2026-11-01-product-interview.md)를 함께 확인한다. 아래 구성과 세부 흐름은 설계 제안이며, 인터뷰의 예시도 고정된 사용 절차로 해석하지 않는다.

## 1. 사용자가 설명한 목표

**SiloLink의 공통 실행 기반을 CLI로 만들고, 여러 LLM 도구에서는 플러그인으로 사용하며, 데스크톱에서는 프로젝트를 보고 실행하고 운영한다.**

사용자가 설명한 핵심 흐름은 다음과 같다.

1. 처음 프로젝트를 구성할 때 플러그인에서 `/silolink init`과 같은 명령을 사용한다.
2. 해당 프로젝트가 SiloLink의 관리 대상이 되고, 정해진 포맷·규격·가이드라인을 따르도록 구성된다.
3. SiloLink Desktop에서 프로젝트를 열고 실행·관리한다.
4. GUI와 대시보드 등을 통해 문서와 작업 운영 상태를 한눈에 확인한다.
5. 데스크톱 안에서도 각 LLM CLI를 사용해 채팅하고, 확장된 작업·문서 관리·작업 운영을 수행한다.

배포·연결 단위는 개별 스킬보다 **플러그인**을 지향한다. 가능하면 여러 LLM 도구에서 사용할 수 있도록 공통 기준을 두되, `$`나 `/` 등 호스트마다 다른 호출 방식에 대응한다. `/silolink init`은 사용자가 제시한 경험의 예시이며, 모든 호스트에서 동일한 문자열을 지원한다고 확정한 것은 아니다.

## 2. 기존 검토와 달라진 판단

[CLI 단독 제공 검토](../research/2026-11-01-silolink-cli-product-direction.md)는 기존 에이전트와 편집기로 기록 재사용을 우선 검증하고, 화면의 필요성은 이후 판단하자는 잠정 권고였다.

이번 설명에서는 데스크톱의 통합 관리 경험이 제품 목표에 명시적으로 포함됐다. 따라서 **CLI를 공통 실행 기반으로 설계하면서 데스크톱의 관리 경험도 초기 검증 범위에 포함하는 방향**으로 권고를 수정한다.

이는 모든 데스크톱 기능을 첫 버전에 구현한다는 뜻은 아니다. 첫 구현 범위와 순서는 별도로 정한다.

## 3. 구성과 책임에 관한 설계 제안

| 구성 | 책임 |
| --- | --- |
| 프로젝트 규격 | 문서·작업·결정의 형식, 식별자, 관계, 상태, 가이드라인, 규격 버전 정의 |
| 공통 코어와 CLI | 프로젝트 초기화, 기록 조회·변경, 검색, 규격 검사 |
| LLM별 플러그인 | 해당 AI가 SiloLink의 명령과 작업 절차를 사용하도록 연결 |
| LLM 실행 연결부 | 데스크톱에서 각 AI CLI 실행, 응답·진행 상태 수신, 중단 처리 |
| 데스크톱 | 프로젝트 탐색, 대시보드, 문서 편집, 채팅, 작업 운영 |

CLI·플러그인·데스크톱은 같은 프로젝트 규격과 공통 처리 기능을 사용하도록 설계한다. 데스크톱에서 CLI 프로세스를 호출할지, 공통 코어를 직접 사용할지 등 내부 연결 방식은 미정이다.

특히 다음 두 연결은 구분한다.

- **외부 AI → SiloLink:** 사용자가 평소 쓰는 AI 도구에서 플러그인을 통해 SiloLink 프로젝트를 조회·변경한다.
- **SiloLink Desktop → AI CLI:** 데스크톱에서 AI CLI를 실행하고 프로젝트 맥락을 전달하며 결과를 받는다.

플러그인을 제공하는 것만으로 데스크톱 안의 AI 실행·채팅 관리가 해결되지는 않는다. 실행 연결부는 공급자별 기능과 제약을 확인해야 한다.

## 4. 여러 LLM에서 공통으로 유지할 기준

보편화의 중심은 호출 기호보다 **작업의 의미와 프로젝트 데이터 규격**에 둔다.

| 공통으로 정의할 것 | 호스트별로 처리할 것 |
| --- | --- |
| 초기화·검색·기록·검토 명령의 의미와 입출력 | 호출 문법과 명령 노출 방식 |
| 문서·작업·결정의 형식과 상태 전환 | 플러그인 설치 위치와 매니페스트 |
| AI에 제공할 작업 절차와 맥락 구성 기준 | 스킬·훅 등 호스트별 확장 기능 |
| 규격 버전과 업그레이드 방식 | AI CLI 실행·응답·세션 처리 방식 |

예를 들어 `silolink init`을 공통 CLI 동작으로 정의하고, 각 호스트의 플러그인이 이를 호출하도록 구성할 수 있다. 공통 원본에서 호스트별 플러그인을 구성해 지침의 중복 관리를 줄이는 방식을 제안한다.

플러그인 안에는 필요한 스킬이나 지침을 포함할 수 있다. Claude Code 공식 문서는 플러그인이 스킬·에이전트·훅·MCP 서버 등을 묶으며, 스킬 호출 예시로 `/my-plugin:review`를 제시한다. OpenAI 공식 문서도 하나의 플러그인이 하나 또는 여러 스킬을 포함할 수 있다고 설명한다. 두 문서는 이 구성의 참고 근거이며 모든 호스트의 형식 호환성을 보장하지 않는다. [Claude Code 플러그인](https://code.claude.com/docs/en/plugins), [OpenAI 스킬 구성](https://developers.openai.com/plugins/build/skills)

## 5. 구체적인 사용 흐름에 관한 제안

### 프로젝트 초기화

플러그인이 공통 초기화 명령을 실행한다. 프로젝트 식별자와 규격 버전을 만들고 문서·작업 구조 및 AI용 지침을 준비한다. 기존 파일을 보존하고, 재실행해도 중복이나 유실이 생기지 않도록 한다.

프로젝트 내부의 관리 정보와 데스크톱에서 프로젝트를 발견·등록하는 방식은 별도로 설계해야 한다. 초기화만으로 모든 데스크톱 설치에 자동 등록된다고 가정하지 않는다.

### 데스크톱에서 열람·운영

데스크톱은 같은 프로젝트 기록을 읽고 문서, 결정, 진행 중인 작업, 검토 대기 항목을 연결해 보여준다. 대시보드는 현재 진행 상황과 사용자가 검토하거나 결정해야 할 항목을 드러내는 방향을 제안한다.

### 문서·작업을 중심으로 AI와 대화

사용자가 문서나 작업을 선택하면 관련 자료·결정·가이드라인을 해당 AI CLI에 전달한다. 대화 결과는 문서 수정이나 작업 상태 변경으로 반영할 수 있게 한다. 제안과 확정 기록을 구별하고, 반영 절차는 후속 설계에서 정한다.

### 다른 AI에서 작업 이어가기

다른 AI 도구에서도 같은 프로젝트 기록과 규칙을 조회해 작업을 이어간다. 공통으로 이어갈 핵심은 **문서·결정·작업 상태와 그 근거**다. 공급자별 대화 세션을 그대로 이전하는 기능은 별도 문제이며 지원이 확인되지 않았다.

## 6. 가이드라인 안내와 규격 검사

플러그인 지침은 AI가 따라야 할 절차를 안내하고, CLI는 검사 가능한 규칙을 확인하도록 역할을 나눈다.

- 안내 대상 예시: 작업 전 관련 결정 조회, 제안과 확정 구분, 결과 기록 절차.
- 검사 대상 예시: 필수 필드, 식별자, 허용된 상태 전환, 깨진 문서 연결, 규격 버전.

초기화나 지침 설치만으로 모든 AI 작업이 규칙을 지킨다고 보장할 수는 없다. 파일 직접 편집과 외부 도구의 변경을 어떻게 검사·반영할지도 설계해야 한다. 형식 검사는 내용의 사실성이나 판단의 적절성 검증과 구분한다.

## 7. 첫 구현 범위와 검증 기준에 관한 제안

첫 구현은 다음 흐름을 작게 연결하는 것을 권고한다.

**프로젝트 초기화 → 플러그인으로 문서·작업 기록 → 데스크톱에서 조회·채팅 → 결과 반영**

먼저 한 LLM 도구로 전체 흐름을 연결하고, 두 번째 연결부를 붙여 공통 규격과 코어가 재사용되는지 확인한다. 첫 LLM만 연결된 상태에서는 범용성이 검증됐다고 판단하지 않는다.

| 검증 항목 | 관찰 가능한 기준 |
| --- | --- |
| 초기화 | 기존 프로젝트를 보존하고, 재실행해도 중복·유실이 없다 |
| 기록 공유 | 플러그인에서 만든 기록을 데스크톱에서 열고, 변경 결과를 다시 조회할 수 있다 |
| 연결된 작업 경험 | 문서·결정·작업의 관계를 확인하고 AI 작업에 필요한 맥락을 전달할 수 있다 |
| 결과 반영 | AI 결과를 문서나 작업에 반영하고 제안·확정 상태를 구분할 수 있다 |
| LLM 간 재사용 | 두 번째 LLM 도구에서도 같은 프로젝트 규격과 기록을 사용한다 |
| 규격 검사 | 잘못된 형식·상태·연결을 오류나 검토 대상으로 드러낸다 |

## 8. 후속 설계에서 정할 사항

- 프로젝트 파일 구조, 문서 형식, 메타데이터와 작업 상태 모델.
- 지원할 첫 LLM 도구와 두 번째 호환성 검증 대상.
- 데스크톱의 최소 화면·채팅 기능 및 AI 결과 반영 절차.
- CLI의 기계 판독용 출력, 오류, 장기 실행 진행 이벤트 규격.
- 외부 편집 반영, 동시 변경 충돌, 기록 복구 방식.
- 설치·업데이트와 프로젝트 규격 마이그레이션 방식.
- 공급자별 인증·이용 범위·실행 및 세션 기능의 실제 지원 여부.

이 항목들은 아직 확정되지 않았다. 본 문서는 제품 방향을 기록하며 세부 구현 계획을 대신하지 않는다.
