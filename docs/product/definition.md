# SiloLink 제품 정의

- 기준일: 2026-11-01, Asia/Seoul
- 근거: 사용자 인터뷰, 후속 정정, 기존 제품 방향과 초기 구상
- 상태: 제품 목표와 요구 정리 완료. PRD·첫 구현 범위·기술 스택은 미확정.

## 1. 목적

SiloLink(사일로링크)는 여러 프로젝트와 AI 도구에 흩어진 기록을 연결하고, 사용자의 실제 작업 맥락을 바탕으로 AI 활용·조사·학습·프로젝트 운영을 지속적으로 지원한다. 이름은 도구별로 분리된 정보 사일로를 연결한다는 의미다.

사용자는 반복되는 모호한 요청, 중복 조사, 파편화된 지식, 프로젝트마다 다른 규칙과 문서, 근거가 불분명한 AI의 시간 예측을 개선하고 싶어 한다. 데스크톱과 플러그인을 설치하고 프로젝트를 초기화한 뒤 평소처럼 작업하면, 축적된 기록에서 유용한 분석과 제안을 먼저 받는 경험을 원한다.

## 2. 대상 사용자와 성공 기준

초기 대상은 여러 사이드 프로젝트를 운영하는 개인 개발자와 바이브 코딩을 시작하는 사용자다. 장기적으로 여러 저장소의 규칙과 문서를 함께 관리하는 개발팀용 공유 플랫폼으로 확장하는 방향을 고려한다.

인터뷰 사용자는 Codex와 Claude Code를 주력으로, Antigravity를 보조로 사용한다. 설계·구현·검토·테스트 역할을 결과와 상황에 따라 나누고 서로의 결과를 검토시킨다. 다른 사용자도 도구 조합과 작업 방식이 다르므로 고정된 역할 분담을 전제하지 않는다.

사용자가 기대하는 변화는 다음과 같다.

- 원하는 결과를 더 구체적으로 요청하고 같은 내용을 다시 조사하는 일을 줄인다.
- 공통·로컬 규칙과 문서를 함께 관리해 여러 프로젝트의 관리 부담을 줄인다.
- 프로젝트별 정책·기술 리포트를 비교해 통합·분리와 새로운 접근의 근거를 얻는다.
- 모인 기록을 읽고 회고·학습·추가 조사와 AI 대화를 이어간다.
- 실제 이력을 근거로 더 현실적인 계획을 받고 업무 진행 상황과 핵심 요소를 빠르게 파악한다.

정량적 개선 목표와 검증 기간은 아직 정하지 않았다. 기존 유사 제품은 인터뷰 당시 사용해 보지 않았으며, 경쟁 제품 대비 개선 효과·외부 수요·전환 의향도 검증하지 않았다.

## 3. 제품 원칙

### 상황에 맞게 지원한다

분석·조사·학습·규칙 관리·플래닝은 상황에 맞게 활용하는 지원 능력이다. 사용자의 요청 방식, 도구별 역할, 작업 순서와 결과 표현은 유연하게 둔다.

사용자는 인터뷰가 특정 사례와 화면을 계속 구체화하면서 고정된 행위만 수행하는 제품으로 이어지는 느낌이라고 지적했다. 시안 트리, 비교표, 보고서, 작업 단계와 아래 사용 예시는 지원 범위를 설명하며 모든 사용자가 따라야 하는 절차가 아니다.

### 근거와 판단 상태를 드러낸다

공식 자료, 논문, 커뮤니티 의견을 구별하고 사용자의 의사결정을 돕는다. 반복 요청이나 부실한 문서를 지식 부족의 확정 근거로 취급하지 않고, 기록에서 확인된 내용과 분석상 추정을 구별하는 방향을 제안한다.

아이디어·제안·확정 결정·구현 결과·검증 결과를 구별하고 원문·근거·적용 조건을 연결하는 것은 공통 설계 원칙으로 제안한다. 구체적인 상태 모델과 판정 규칙은 PRD·설계에서 정한다.

### 작업 맥락을 도구 사이에서 이어간다

외부 AI 도구에서 만든 기록을 데스크톱에서 읽고, 데스크톱에서 정리한 기록을 다음 AI 작업에서 재사용한다. 이어갈 핵심은 문서·결정·작업 상태와 근거다. 공급자별 대화 세션 자체의 이전은 별도 기술 검증 대상이다.

## 4. CLI·플러그인·데스크톱

사용자가 설명한 제품 구성은 CLI를 공통 실행 기반으로 두고, 여러 LLM 도구에서는 플러그인으로 사용하며, 데스크톱에서 프로젝트를 보고 실행·운영하는 형태다. 배포·연결 단위는 개별 스킬보다 플러그인을 지향한다.

다음 책임 구분은 설계 제안이다.

| 구성 | 역할 |
| --- | --- |
| 프로젝트 규격 | 문서·작업·결정의 형식, 식별자, 관계, 상태, 가이드라인과 규격 버전 |
| 공통 코어·CLI | 초기화, 기록 저장·조회·변경·검색, 규격 검사 |
| 도구별 플러그인 | 각 AI 도구에 명령과 작업 지침을 제공하고 공통 기능으로 연결 |
| AI 실행 연결부 | 데스크톱에서 외부 AI CLI 실행, 이벤트·응답·권한·중단 처리 |
| 데스크톱 | 프로젝트·문서 탐색, 분석·알림·회고·학습, 채팅과 작업 운영 |

‘외부 AI → SiloLink 기록 기능’과 ‘SiloLink Desktop → AI CLI 실행’은 별도 연결이다. 플러그인만으로 데스크톱의 AI 실행·채팅 관리가 완성되는 것은 아니다.

공통화의 중심은 호출 기호보다 명령의 의미·입출력과 프로젝트 데이터 규격에 둔다. `/silolink init`은 사용자 경험의 예시이며, 호스트에 따라 `$`·`/` 등 호출 문법과 배포 형식이 다를 수 있다. 플러그인에 필요한 스킬·지침을 포함하고 공통 원본에서 호스트별 구성을 만드는 방안을 제안한다.

데스크톱이 CLI를 호출할지 코어를 직접 사용할지, MCP 연결이 필요한지, 데스크톱 종료 중 CLI를 어떻게 운영할지는 미정이다. 기술 근거와 검증 과제는 [CLI·플러그인 연동 조사](../research/cli-integration.md)에 정리한다.

## 5. 지원할 경험

### 기존 프로젝트 연결과 문서 정돈

사용자는 기존 프로젝트들에 `silolink init`을 실행하고 과거 문서를 SiloLink의 관리 구성으로 재구조화한 뒤, 데스크톱에서 살펴보며 회고하고 싶다고 밝혔다.

기록은 프로젝트에 따라 채팅에만 있거나, 정리된 `docs/`, 흩어진 Markdown, 부실한 Markdown으로 존재한다. 초기 수집과 재구조화는 이런 차이를 고려해야 한다. 수집 가능한 기록·기존 문서의 보존과 변경·초기화 재실행·데스크톱 등록 방식은 설계 및 검증 대상이다.

### 요청·선택 패턴과 지식 연결

- 자주 하는 요청, 궁금해하는 주제, 모호하게 사용한 용어와 추가 학습 후보를 보여준다.
- 여러 프로젝트의 반복 조사와 파편화된 지식을 연결하고 다른 프로젝트에도 고려할 발견을 드러낸다.
- 프로젝트를 합치거나 나눌 때의 장단점과 경계를 판단하도록 돕는다.

인터뷰 사용자는 ‘잘해줘’, ‘그거 말고’ 같은 요청을 반복했고, 시안을 본 뒤 자신의 기준을 발견하는 경우가 많았다. 시안을 바로 선택하거나 개선안을 분기해 재선택하며, 선택 이유를 자세히 설명할 때와 짧게 선택만 할 때가 모두 있다. 이 탐색 과정을 분석하되 특정한 시안 작성·선택 절차를 강제하지 않는다.

### 자동 안내·학습·회고

평소 작업 중 백그라운드 분석으로 사용 습관·요청 방식의 개선안, 분석 보고서, 용어 가이드를 제공한다. 사용자는 다음 알림 방식을 원한다.

| 종류 | 요구 |
| --- | --- |
| 패턴 발견 | 의미 있는 반복 요청·모호한 표현 등을 발견하면 즉시 알림 |
| 일간 회고 | 데스크톱에 설정한 하루 마감 시각을 기준으로 알림 |
| 주간 회고 | 일간 회고와 별도의 주간 보고서 |

학습 가이드는 실제 요청 문맥, 정확한 의미와 레퍼런스, 개선된 요청 예시, 현재 프로젝트에 적용할 과제까지 지원한다. 모인 기록은 학습과 일정 관리로도 이어지길 원한다. 탐지 기준·알림 중복 처리·주간 발행 시점·일정 관리 상세 기능은 미정이다.

### 공통·로컬 규칙과 문서 관리

컨벤션과 문서 관리 방식을 중심으로 공통 규칙과 프로젝트별 로컬 규칙을 한눈에 관리한다. 유사 규칙을 상위 규칙으로 올려 중앙관리하거나 프로젝트별 차이를 유지할 근거를 제공한다.

프로젝트별 정책·조사·학습·데이터 구성의 같은 점과 다른 점, 합치거나 나눌 때의 영향을 비교한다. 사용자가 제안을 읽고 타당하다고 판단하면 AI와 규칙을 다듬고, 선택한 프로젝트들의 문서 구성까지 실제로 정리하는 경험을 원한다.

### 레퍼런스 기반 조사와 채팅

최적화 과정과 정확한 레퍼런스 기반 기술·자료 조사는 필수 핵심 기능이다. 데스크톱 채팅에서 문서에 관한 질문을 풀고, 여러 프로젝트 기록을 기준으로 새로운 분석과 접근의 가치를 조사한다. 사람이 읽고 공유할 기술 정리서를 만드는 요구도 있다. 출력 형식은 미정이다.

| 자료 | 요구 |
| --- | --- |
| 공식 자료 | 반드시 확인 |
| 논문 | 기술·주제 범위에 따라 검토 |
| 커뮤니티 | 관련 실사용자의 의견·논쟁을 공식 자료와 분리해 검토 |

의견이 엇갈리는 부분을 한눈에 보여 의사결정을 돕는다. 주장별 이유·버전·환경·적용 조건과 현재 프로젝트와의 관계를 비교하는 방향을 제안한다. 모든 조사에 구현 실험을 붙이는 요구는 없으며, 아키텍처처럼 조건이 복합적인 결정도 유연하게 지원한다. 검증 실험의 지원·실행 범위는 미확정이다.

### 실제 이력에 기반한 플래닝

AI의 ‘3일’, ‘5일’ 같은 예상이 누구의 기준인지 불분명하고 질문마다 달라지는 문제를 개선하고 싶다고 밝혔다. 시간 기록의 주요 목적은 과거 실적을 근거로 신규 프로젝트의 AI 판단과 계획을 개선하는 것이다.

- 기능 단위와 설계·구현·검토·테스트 같은 작업 단위를 함께 분석한다.
- 본인의 투입 시간, AI 실행·대기 시간, 시작부터 완료까지의 전체 경과 시간을 살펴본다.
- 사용자가 직접 테스트한 시점을 최종 완료 판단의 기준으로 삼는다. 테스트 후 수락·재작업 상태의 상세 모델은 미정이다.
- PRD·기술 문서·아키텍처·작업 기록을 연결해 업무 진행 상황과 핵심 파악에 드는 수고를 이해한다.

기능·작업·AI 세션을 연결하고, 측정치와 추정치를 구별하며, 겹치는 시간을 단순 합산하지 않는 구조를 제안한다. 계획에는 유사 사례·작업 기준·가정·범위·예상 변경 이유를 연결하는 방향이다. 실제 측정 가능성과 예측 개선 효과는 검증 전이다.

## 6. 개발 전 남은 결정과 검증

| 항목 | 남은 사항 |
| --- | --- |
| PRD·첫 구현 범위 | 전체 제품 요구에서 첫 구현과 수용 기준을 정해야 함 |
| 초기 OS | Windows 우선인지 macOS도 동시 지원할지 미정 |
| 저장·동기화 | 원본·분석 결과의 로컬 저장, 여러 PC 동기화와 서버 필요 여부 미정 |
| AI 연결 | 공급자별 인증·구독 이용 범위·실행·이벤트·취소·세션 지원 확인 필요 |
| 기록 수집 | Codex·Claude Code의 과거·진행 중 기록을 어떻게 수집할지 검증 필요 |
| 프로젝트 규격 | 식별자·파일 형식·메타데이터·상태·워크트리·등록·버전 이행 미정 |
| 변경 관리 | 외부 편집·동시 수정·중복·충돌·복구와 규칙 상속·예외 미정 |
| 분석·계획 | 근거 연결·패턴 탐지·알림·시간 측정·예측 보정의 실효성 검증 필요 |
| 기술 스택 | 앱 프레임워크·언어·저장 엔진·색인·검색 방식 미선정 |
| 후속 확장 | 팀 공유·배포·업데이트·설치 경험의 상세 범위 미정 |

사용자의 기존 AI 구독과 CLI 환경을 활용하는 것이 비용 설계 목표다. 로컬 저장과 외부 모델로 전달되는 처리는 구별하며, 완전 오프라인·모든 공급자의 동일 기능·전체 기록의 자동 수집을 보장하지 않는다.

초기화 반복의 안전성, 원본·근거 보존, 정확한 프로젝트 귀속, 외부 편집 반영, 부분 실패·중단·재시도, 두 AI 도구 사이의 기록 재사용은 검증 기준 후보로 제안한다. 필수 필드·식별자·상태·링크 같은 형식 검사는 내용의 사실성 검증과 구별한다.

## 7. 판단 경과와 다음 단계

초기에는 기존 편집기와 CLI만으로 기록 재사용을 먼저 검증하는 권고가 있었다. 이후 사용자가 데스크톱의 분석·채팅·회고·관리 경험을 명시했으므로 현재 제품 방향에는 데스크톱도 포함한다. CLI는 공통 실행 기반이며, 화면의 필요성을 다시 유보하는 과거 권고는 현재 방향으로 사용하지 않는다.

다음 단계의 권고는 PRD v0.1 작성, 기록 수집 기술 검증, 첫 사용 흐름 개발이다. 전체 요구를 한 번에 구현하거나 사례별 절차를 고정하는 결정은 아니다. [유사 제품 조사](../research/alternatives.md)와 [Basic Memory 분석](../research/basic-memory.md)의 비교·검증 과제도 참고한다.
