# SiloLink 제품 인터뷰 정리

- 인터뷰·정리일: 2026-11-01, Asia/Seoul
- 근거: 현재 프로젝트에서 사용자가 답변한 제품 인터뷰와 후속 정정
- 목적: PRD 작성에 앞서 사용자 요구, 설계 제안, 미정 사항을 보존한다.
- 상태: 사용자 답변 정리. PRD·첫 구현 범위·기술 스택은 미확정이며 제품 구현은 시작하지 않았다.
- 관련 문서: [CLI·플러그인·데스크톱 제품 방향](2026-11-01-cli-plugin-desktop.md)

## 1. 제품의 중심과 유연성

사용자가 여러 프로젝트와 AI 도구를 활용하는 동안, 그 기록과 맥락을 이해해 더 나은 AI 사용·조사·학습·프로젝트 운영을 지원한다.

사용자는 특정 사례를 계속 구체화하는 인터뷰가 범용 지원보다 고정된 행위만 수행하는 제품으로 이어지는 느낌이라고 지적했다. 따라서 다음 기준을 유지한다.

- 분석·조사·학습·규칙 관리·플래닝은 상황에 맞게 활용하는 지원 능력이다.
- 사용자의 요청 방식, 도구별 역할, 작업 순서와 결과 표현은 유연하게 둔다.
- 인터뷰에 등장한 시안 트리, 비교표, 보고서, 작업 단계는 사용 사례다. 모든 사용자가 따라야 하는 고정 절차로 확정하지 않는다.
- 사용자의 의사결정을 돕고, 제안과 근거를 확인하며 AI와 내용을 다듬을 수 있게 한다.

## 2. 대상 사용자와 확장 방향

초기 대상은 여러 사이드 프로젝트를 운영하는 개인 개발자와 바이브 코딩을 시작하는 사용자다. 개인의 실제 사용 패턴을 바탕으로 관리된 AI 사용 경험을 제공한다.

사용자는 현재 Codex와 Claude Code를 주력으로, Antigravity를 보조로 사용한다. 설계·구현·검토·테스트 역할은 결과와 상황에 따라 달라지며 고정되어 있지 않다. 서로의 결과를 검토하거나 작업을 나누기도 한다. 다른 사용자의 다양한 조합과 방식도 지원하고 싶다고 밝혔다.

장기적으로 여러 저장소의 규칙과 문서를 함께 관리하는 개발팀용 공유 플랫폼으로 확장하는 방향을 고려한다. 초기 팀 기능 구현이나 지원 도구 전체의 동시 구현을 확정한 것은 아니다.

## 3. 첫 사용과 기존 프로젝트 싱크업

사용자가 설명한 첫 사용 흐름은 다음과 같다.

1. 기존에 작업하던 프로젝트들에 `silolink init`을 실행한다.
2. 과거 문서가 있으면 SiloLink가 관리하는 문서 구성으로 재구조화해 프로젝트를 싱크업한다.
3. 데스크톱에서 모인 기록과 분석을 살펴보고 회고한다.

기록 상태는 프로젝트마다 다르다. 채팅에만 남은 내용, 정리된 `docs/`, 흩어진 Markdown, 부실하게 작성된 Markdown을 모두 고려해야 한다. 초기 수집 범위·문서 형식·실제 이동 및 변경 방식은 미정이다.

설치와 초기화 후 평소처럼 사용하면 백그라운드 데스크톱이 기록을 분석하고 먼저 안내하는 경험을 원한다. 과거 기록과 진행 중인 작업을 실제로 수집할 수 있는 방식·범위는 기술 검증이 필요하다.

## 4. 요청·선택 패턴과 지식 분석

사용자는 다음을 한눈에 보고 싶다고 밝혔다.

- 자주 하는 요청과 궁금해하는 주제.
- 모호하게 사용한 용어와 추가 학습이 필요한 내용.
- 여러 프로젝트에 파편화된 지식과 반복 조사.
- 한 프로젝트의 발견이나 질문이 다른 프로젝트에도 영향을 주는 지점.
- 프로젝트를 합치거나 분리할 때 고려할 장단점과 경계.

사용자는 ‘잘해줘’, ‘그거 말고’ 같은 요청을 반복한 경험을 설명했다. 원하는 모습이 막연한 상태에서 시안을 보고 기준을 발견하는 경우가 많았다. 시안을 바로 선택하거나, 선택 후 개선안을 분기시켜 비교·재선택하기도 했다. 선택 이유는 자세히 설명할 때도 있고 짧게 선택만 할 때도 있었다.

설계 유의점: 반복 요청, 부실한 문서, 명시되지 않은 선택 이유를 지식 부족의 확정 근거로 취급하지 않는다. 기록에서 직접 확인되는 내용과 분석상 추정을 구별하는 방향을 제안했다. 이 구분의 세부 판정 규칙은 미정이다.

## 5. 자동 안내·학습·회고

사용자가 원하는 안내는 실사용을 개선하는 가이드, 분석 보고서, 용어 가이드, 프롬프트·요청 개선안이다. 데스크톱에서 한눈에 확인하고 학습·기록·일정 관리로 이어지길 원한다.

알림 요구는 다음과 같다.

| 종류 | 사용자 요구 |
| --- | --- |
| 패턴 발견 | 반복 요청·모호한 표현 등 의미 있는 패턴을 발견하면 즉시 알림 |
| 일간 회고 | 데스크톱에서 하루 마감 시각을 설정하고 그 시각을 기준으로 알림 |
| 주간 회고 | 일간 회고와 별도로 주간 단위 보고서도 제공 |

학습 가이드는 ‘실제 요청 문맥 → 정확한 의미와 레퍼런스 → 개선된 요청 예시 → 현재 프로젝트에 적용할 과제’까지 연결하는 구성을 사용자가 수용했다. 이는 가이드의 지원 범위이며, 모든 사용자에게 강제하는 학습 순서는 아니다.

알림의 실제 탐지 기준·중복 억제·주간 발행 시점·일정 관리 상세 기능은 미정이다.

## 6. 프로젝트 간 규칙·문서 관리와 개선 반영

컨벤션과 문서 관리 최적화는 대표적인 공통화 대상이다.

- 공통 규칙과 프로젝트별 로컬 규칙을 한눈에 관리한다.
- 유사한 규칙을 상위 규칙으로 올려 중앙관리하는 방향을 지원한다.
- 프로젝트별 정책·지식 조사·학습 조사·데이터 구성의 같은 점과 다른 점을 비교한다.
- 정책·프로젝트를 합치거나 나눌 때 판단에 필요한 인사이트를 제공한다.
- 여러 프로젝트의 문서·기술 리포트를 모아 보고 회고한다.

사용자는 제안을 읽고 타당하다고 판단하면 AI와 공통 규칙을 다듬고, 선택한 프로젝트들의 문서 구성까지 실제로 정리되길 원한다.

규칙 우선순위·상속·예외 표현·변경 반영 및 복구 방식은 미정이다.

## 7. 근거 기반 조사와 데스크톱 채팅

최적화 과정과 정확한 레퍼런스에 기반한 기술·자료 조사는 필수 핵심 기능이다. 사용자는 데스크톱에서 기록을 보며 실시간 채팅으로 궁금증을 풀고, 여러 프로젝트의 문서를 기준으로 새로운 분석과 접근의 가치를 조사하고 싶다고 밝혔다.

| 자료 | 요구 |
| --- | --- |
| 공식 자료 | 반드시 확인 |
| 논문 | 기술·주제 범위에 따라 함께 검토 |
| 커뮤니티 | 관련 실사용자가 모이는 곳의 의견·논쟁을 공식 자료와 분리해 함께 검토 |

공식의 긍정적인 설명과 커뮤니티의 찬반 논쟁을 함께 보고 선택 이유를 판단하고 싶다고 밝혔다. 의견이 엇갈리는 부분은 한눈에 보기 쉽게 제공해 의사결정을 도와야 한다.

자료별 주장·버전·환경·적용 조건과 프로젝트 적합성을 비교하는 것은 설계 제안이다. 모든 조사에 구현 실험을 붙이는 요구는 없다. 특히 아키텍처처럼 판단 조건이 복합적인 문제에서 ‘작은 검증 실험’을 일률적인 절차로 삼는 접근에는 사용자가 의문을 제기했다. 검증 실험의 지원 여부·실행 범위는 미확정이다.

## 8. 작업 실적과 개인화된 플래닝

사용자는 AI의 ‘3일’, ‘5일’ 같은 예상이 누구의 작업 기준인지 불분명하고 질문할 때마다 달라지는 점을 문제로 설명했다.

시간 기록의 주요 목적은 과거 실적을 근거로 신규 프로젝트의 AI 판단과 플래닝을 개선하는 것이다. PRD·기술 문서·아키텍처·작업 기록을 연결해 업무 진행 상황과 핵심 파악에 드는 수고도 이해하고 싶다고 밝혔다.

- 기능 단위와 설계·구현·검토·테스트 같은 작업 단위를 모두 분석하고 싶다.
- 본인의 실제 투입 시간, AI 실행·대기 시간, 시작부터 완료까지의 전체 경과 시간을 모두 살펴보고 싶다.
- 사용자 직접 테스트 시점을 최종 완료 판단의 기준으로 삼고 싶다고 답했다. 테스트 결과에 따른 최종 수락·재작업 상태의 세부 모델은 미정이다.

기능과 그 안의 작업에 AI 세션·실행 기록을 연결해 여러 관점으로 집계하는 구조를 제안했다. 이 구조와 세부 집계 규칙은 아직 확정하지 않았다.

수집 가능한 시간과 추정 시간을 구별하고, 겹치는 시간을 단순 합산하지 않으며, 유사 사례·가정·범위·추정 변경 이유를 함께 보여주는 방향을 제안했다. 실제 측정 가능성, 예측 정확도와 개선 효과는 검증하지 않았다.

## 9. 사용자가 기대하는 변화

- 원하는 결과를 더 구체적으로 요청한다.
- 같은 내용을 다시 조사하는 일을 줄인다.
- 공통·로컬 규칙과 문서를 함께 관리해 여러 프로젝트의 관리 부담을 줄인다.
- 모인 기록에서 정책 통합·분리와 새로운 접근에 관한 인사이트를 얻는다.
- 회고·학습·추가 조사와 실시간 AI 대화를 이어간다.
- 실제 작업 이력을 기반으로 더 설명 가능하고 현실적인 계획을 받는다.
- 진행 중인 업무와 핵심 요소를 더 잘 파악한다.

정량적인 개선 목표와 검증 기간은 아직 정하지 않았다.

## 10. PRD·개발 착수 전에 남은 사항

| 항목 | 현재 상태 |
| --- | --- |
| PRD와 첫 구현 범위 | 작성·범위 확정 전. 위 전체 요구를 첫 버전의 동시 구현 약속으로 해석하지 않음 |
| 초기 지원 OS | Windows 우선 여부, macOS 동시 지원 여부 질문에 아직 답변 없음 |
| 원본·분석 결과 저장과 동기화 | 로컬 우선 여부, 여러 PC 간 동기화 필요 여부 질문에 아직 답변 없음 |
| AI 데이터 전달 | 원본의 로컬 저장과 별개로 설계 필요 |
| 기록 수집 | Codex·Claude Code의 과거·진행 중 기록 접근과 수집 가능 범위를 개발 측에서 검증 필요 |
| 프로젝트 규격과 규칙 모델 | 문서 형식·메타데이터·프로젝트 경계·상속·예외·충돌·복구 방식 미정 |
| 자동 분석과 측정 | 패턴 탐지·근거 연결·알림·시간 측정·예측 보정의 실효성 검증 필요 |
| 기술 스택과 실행 연결 | 아직 선택하지 않음 |

권고된 후속 순서는 ‘인터뷰 결과 정리 → PRD v0.1 → 기록 수집 기술 검증 → 첫 사용 흐름 개발’이다. 이는 개발 착수나 세부 설계의 사용자 확정으로 기록하지 않는다.

이번 정리 요청은 폴더 정리와 Git 커밋·푸시다. PRD 작성이나 제품 구현은 후속 작업으로 남겨둔다.
