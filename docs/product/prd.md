## 1. 제품 비전

SiloLink는 대화·문서 수집기가 아니다. 사용자가 평소처럼 Codex·Claude Code 같은 AI 도구를 쓰기만 하면, 뒤에서 대화·AI 답변·문서를 분석해 사용자를 파악하고 그 기록을 근거로 옆에서 돕는 **AI 작업 비서**를 지향한다. 기록이 얼마나, 어떻게 연결되어 있고 어떻게 활용될 수 있는지가 제품의 핵심이다.

가장 큰 목적은 **사용자의 AI 활용 능력을 키우는 것**이다. 용어나 배경지식을 몰라 ‘잘 해줘’, ‘알아서’로 넓게 요청하던 사용자가 자기 요청의 빈틈을 알아차리고 더 구체적인 요구를 던지도록 돕는다.

이름은 도구별 정보 사일로(silo)를 연결(link)한다는 뜻이다.

### 사용자 진술 — 2026-11-08

- 설치한 뒤 기존에 쓰던 Claude·Codex 등에 연결만 해 두면, 내 대화와 AI 답변을 분석해 내가 어떤 지식을 모르고 ‘잘’, ‘알아서’라고 표현했는지 찾아 요구사항을 더 잘 던질 수 있게 관리한다.
- 실제 사례: “UI/UX 잘 적용해서 작업해줘”라고 자주 요청했다. 이를 용어를 모르고 넓은 범위로 요청한 것으로 잡아내 용어를 정리하고 알림으로 준다. 대화 중에 트리거되어 미리 설정한 CLI를 실행하고 용어집을 만든다. 이 흐름을 만들며 테스트하는 중이다.
- 계속 쓰면 앞서 조사한 지식을 중복으로 조사하지 않게 하고, 바로 문서화해 기술 보고서처럼 회사 보고용으로도 쓸 수 있다.
- AI에게 맡긴 작업을 기능별로 나눠 걸린 시간을 관리한다. 비슷한 요구나 처음부터 다시 만드는 경우 ‘대략 이 정도’가 아니라 기록에 근거해 얼마나 걸리는지 보고한다. AI도 가짜 기간을 말하지 않고 이 기록을 참조해 얼마나 더 빠르게 만들 수 있는지 보고 개발 계획을 세운다.
- 하루가 지나면 그날 작업한 내용을 자동으로 일지로 정리하고, 주간 일지로도 자동 정리한다.
- 프로젝트가 늘어나 한 프로젝트에서 추가하면 좋은 하네스 규칙이 발견되거나 추가되면, 이를 합쳐 다른 프로젝트에도 적용한다.
- 이후에는 많이 쌓인 작업 문서로 브레인스토밍·나의 페인포인트·다른 기술적 접근을 확장해 나간다.
- 기록 관리와 빠른 지식 확장을 위해 어시스턴트처럼 계속 학습·정리하고, 그 내용을 근간으로 보고 자료를 추출할 수 있어야 한다. AI를 사용하기만 하면 뒤에서 나를 파악하고 그것을 기반으로 옆에서 다 해 주는 비서가 제공하려는 상이다.

## 2. 해결할 문제

v0.1 인터뷰에서 사용자가 설명한 문제다. 비전의 각 목표는 이 문제에서 나온다.

| 문제 | 실제로 막히는 지점 | 목표 |
| --- | --- | --- |
| 원하는 결과가 막연해 ‘잘해줘’, ‘그거 말고’를 반복하고, 결과나 시안을 본 뒤 자신의 기준을 발견한다 | 요청 습관·모르는 용어·발견한 기준이 남지 않아 매번 처음부터 맞춘다 | G1 |
| 같은 내용을 다시 조사하고, 한 프로젝트의 지식이 다른 프로젝트에도 유효한지 알아차리기 어렵다 | 조사 결과가 근거·조건 없이 대화 속에 묻혀 재사용되지 않는다 | G2 |
| 기록이 채팅·정리된 `docs/`·흩어진 Markdown에 나뉘고 정리 수준도 다르다 | 무엇이 어디 있는지 모르고 정리 자체가 부담이다 | G0, G2, G4 |
| 컨벤션·문서 관리·정책의 공통점과 차이를 비교하고 공통·로컬 규칙을 운영하기 어렵다 | 규칙이 프로젝트마다 갈라지고, 맞추려 해도 영향과 복구가 걱정된다 | G5 |
| AI의 ‘3일’, ‘5일’ 같은 예상이 누구 기준인지 불분명하고 질문마다 달라진다 | 나의 실제 작업 속도라는 근거가 없다 | G3 |

사용자는 시안을 선택하고 개선안을 분기·비교하기도 하며, 선택 이유를 길게 설명할 때와 선택만 남길 때가 모두 있다. AI 도구의 역할도 상황에 따라 바뀐다. 제품은 이런 다양성을 지원한다.

| 여러 사이드 프로젝트를 운영하는 개인 개발자 | 기록 재사용, 보고 자료, 공통·로컬 규칙 비교, 실적 기반 계획, 여러 프로젝트의 업무 파악 | G2~G5 |

인터뷰 사용자는 Codex·Claude Code를 주력, Antigravity를 보조로 사용한다. 설계·구현·검토·테스트를 도구별로 고정하지 않으며, 한 도구의 결과를 다른 도구로 검토하기도 한다. 첫 설치 기준의 페르소나는 ‘개발 지식이 없고 바이브 코딩에 관심이 생겨, 문서 관리와 AI 활용에 도움이 된다고 듣고 처음 설치하려는 사람’이다.

성공은 더 구체적인 요청, 중복 조사 감소, 프로젝트 관리 부담 감소, 회고·학습과 새로운 접근의 발견, 실제 이력에 근거한 계획, 업무 핵심의 빠른 파악으로 판단한다. 정량 목표는 사용 기준선을 확보한 뒤 정한다. 경쟁 제품 대비 효과·수요·전환 의향은 검증 전이다.

## 5. 원칙

### 비서로서의 원칙

- **뒤에서 동작하되 범위는 사용자가 안다.** ‘알아서’는 사용자가 모르는 수집이 아니다. 무엇을 수집·분석하고 어떤 내용을 어느 외부 AI에 보내며 이용 한도를 얼마나 쓰는지 확인하고 바꿀 수 있어야 한다. 기본값을 어떻게 둘지는 13절에서 정한다.
- **진단이 아니라 제안한다.** ‘모른다’고 단정하지 않고 ‘범위가 넓어 보이는 표현과 쓸 수 있는 용어 후보’로 제안한다. 의도적으로 넓게 맡긴 요청, 시안을 보며 기준을 찾는 반복 탐색은 정상적인 작업 방식으로 존중한다.
- **근거가 명확한 예상을 준다.** 소요 시간은 비교한 실적·조건·범위를 함께 보여 주는 예상이다. 근거가 부족하면 잠정 추정으로 표시하고, 기록이 없는 상태에서 확정 기간을 만들지 않는다.
- **성장을 보여 주되 판정하지 않는다.** 이후 요청의 변화는 근거와 비교 기간으로 보여 주며, 자료를 열었다는 사실만으로 이해 완료를 확정하지 않는다. 변화는 LLM의 판정이 아니라 같은 입력에 같은 결과를 내는 결정적 계산으로 보인다.
- **점수·등급으로 사람을 표시하지 않는다.** ‘68점’, ‘미흡’ 같은 평가 대신 근거 원문, 쓸 수 있는 용어, 더 구체적인 요청 예시를 보여 준다.
- **요청을 바꾸지 않고 옆에서 알린다.** 사용자의 요청을 대신 고쳐 보내거나 모르게 지시를 덧붙이지 않는다. 대화 중에는 기록하고 알리며, 용어집을 다음 작업 맥락으로 넣는 것은 사용자가 켠 경우에만 한다. 당장의 답을 좋게 만드는 것보다 사용자가 다음 요청을 스스로 더 잘 쓰게 되는 것이 목적이다.
- **근거 표시를 통일한다.** 분석·용어집·노트·일지·보고서의 각 주장에 `기록에서 확인`·`추정`·`모호`·`미확인` 중 하나를 붙이고, 확인한 주장에는 원문(도구·세션·시각·화자) 인용을 연결한다.

### 범용 지원 원칙 — v0.1 유지

분석·조사·학습·규칙 관리·플래닝은 상황에 따라 활용하는 능력이다. 사용자의 요청 문법, 작업 순서, AI 역할, 결과 표현을 단일 절차로 고정하지 않는다. 시안 트리·비교표·보고서·설계 단계는 사용 가능한 표현과 예시다.

근거와 판단 상태를 드러내고 사용자의 의사결정을 돕는다. 기록으로 확인한 사실과 분석상 추정, 아이디어·제안·결정·구현·검증 상태를 구별한다. 유사성만으로 원문·규칙을 자동 병합하지 않고, 제안 열람을 변경 확정으로 취급하지 않는다. 지원하지 않는 기능, 일부만 성공한 결과, 데이터 없는 개인화를 성공이나 예시 수치로 채우지 않는다.

Claude의 [공식 제품 제공·인증 조건](https://code.claude.com/docs/en/legal-and-compliance)은 사용자가 미수정 CLI에 자기 구독으로 로그인하는 호스팅과 제3자 자체 로그인·토큰 중계를 구별한다. [연동 조사](../research/cli-integration.md)를 기준으로 로컬 CLI 방식을 설계한다. 로컬 저장과 외부 AI로 전달하는 데이터는 별도 범위다. 전체 기록의 완전한 자동 수집, 완전 오프라인, 공급자별 동일 기능은 검증된 전제가 아니다.

## 7. 핵심 경험

### 7.1 성장 루프 — G1

1. 사용자가 평소처럼 연결된 AI 도구에 요청한다.
2. SiloLink가 요청 시점이나 수집 직후에 범위가 넓거나 용어 없이 설명한 요청을 후보로 감지한다.
3. 관련 용어·개념·의미 후보와 근거 원문을 용어집 항목으로 정리한다. 같은 용어는 근거를 누적한다.
4. 사용자에게 알린다. 알림에는 요청 원문, 넓다고 본 이유, 쓸 수 있는 용어, 더 구체적인 요청 예시가 들어간다.
5. 사용자는 후보를 수락·수정·제외하거나 대화·학습으로 이어 간다.
6. 이후 같은 주제의 요청이 구체적으로 바뀌었는지 근거와 비교 기간을 함께 보여 준다.

예시: “UI/UX 잘 적용해서 작업해줘”는 영역명만 지정하고 기준을 ‘잘’에 맡긴 요청이다. 용어 후보로 정보 구조·시각적 위계·간격 체계·상호작용 상태·접근성·반응형 배치를 제시하고, “버튼과 입력 필드에 포커스·비활성 상태를 추가하고 간격을 8px 단위로 맞춰줘” 같은 요청 예시를 보여 준다. 후보와 예시는 사용자의 실제 프로젝트 문맥을 따르며 위 목록은 설명을 위한 예다.

### 7.2 첫 사용과 지속 사용

첫 사용: 설치 → 앱이나 도구 안의 스킬로 Codex·Claude Code·Antigravity 연결 → 프로젝트 폴더 연결 → 문서 현황 확인 → 기록 수집 시작. 사용자가 `init` 같은 하위 명령을 외우지 않아도 된다.

지속 사용: 평소 AI 도구를 쓰는 동안 기록이 쌓이고, 넓은 요청과 반복 패턴을 발견해 알린다(G1). 하루와 한 주가 끝나면 일지가 만들어진다(G4). 조사는 노트로 남아 다음 질문에서 재사용되고 보고 자료로 추출된다(G2). 작업 실적이 쌓이면 다음 계획의 근거가 된다(G3). 프로젝트가 늘면 좋은 규칙을 다른 프로젝트와 비교·적용한다(G5). 자료가 충분히 쌓이면 브레인스토밍과 새로운 접근으로 확장한다(G6).

이 설명은 연결되어야 할 경험이며 반드시 거쳐야 하는 화면 순서가 아니다. 사용자는 문서·대화·분석·프로젝트 등 필요한 지점에서 시작할 수 있다.

## 8. 기능 요구와 수용 기준

요구의 목적은 인터뷰와 2026-11-08 사용자 진술에 근거한다. 상세 수용 기준은 구현·사용자 검증을 위한 제안이다. 각 요구 제목의 괄호는 3절 목표와 우선순위다.

설치 설명에서 CLI·스킬·init의 차이를 먼저 배우게 하지 않는다. 이 페르소나는 기존 개인 개발자 대상을 대체하지 않으며 첫 진입의 기준으로 추가한다.

첫 수용 기준은 ‘명령어를 입력하지 않고 제공받은 패키지를 등록하고 Codex 설치 목록에서 발견할 수 있으며, 앱에서는 폴더 선택과 연결만으로 실제 문서의 첫 결과에 도달한다’이다. 지원하지 않는 파일, 읽기 실패, 기록 미수집과 공개 배포 미완료를 성공으로 표시하지 않는다.

설치 후 연결: 앱의 세 도구 연결 버튼은 실제 사용자 스킬 파일을 만들고, 메타데이터가 가리키는 동봉 실행 파일로 초기화·문서 조회가 동작해야 한다. 등록 상태 확인은 무수정이며 수정된 스킬·다른 설치·링크는 보존한다. 지원하지 않는 호스트나 임의 실행 파일 경로를 화면에서 등록할 수 없어야 한다. ‘연결됨’은 스킬 등록의 상태이며 호스트 설치·로그인이나 실제 모델 실행의 성공을 뜻하지 않는다.

기능 발견: 사용자가 CLI 하위 명령을 외우지 않아도 스킬 목록에서 프로젝트 연결·문서 확인·기록 가져오기·변경안 검토/적용/이력/복구 등을 각각 선택한다. 통합 `silolink`와 기능별 진입점을 한국어 이름·설명·기본 요청과 함께 설치한다.

배포: PR·main 검증과 태그 게시의 권한을 구별하며 검사·앱 UI 검증에 실패한 결과를 공개하지 않는다. 태그와 앱·CLI·프런트엔드·플러그인 버전이 일치해야 하고 설치 EXE·플러그인 ZIP·체크섬을 전달한다. 게시 중 실패는 초안으로 보존하고 이미 공개한 릴리스는 자동 덮어쓰지 않는다.

### G0 기반

#### R01. 프로젝트 연결과 기존 문서 싱크업 (G0·P0)

프로젝트를 초기화하고 채팅·문서 등 서로 다른 상태의 과거 기록을 연결하며 문서 구성을 정돈한다.

- R01-A: 기존 문서·흩어진 Markdown·문서 없는 프로젝트를 각각 연결할 수 있고, 수집한 것·수집하지 못한 것·판단이 필요한 것을 확인할 수 있다.
- R01-B: 초기화 재실행으로 프로젝트나 기록이 중복되지 않고 기존 내용이 조용히 덮어써지지 않는다.
- R01-C: 재구조화 제안은 이동·통합·재작성·삭제와 관련 링크 영향을 보여준다. 적용 후 실제 파일과 링크가 일치하고, 변경 전 상태와 적용 결과를 추적할 수 있다.
- R01-D: 같은 폴더명·여러 경로·워크트리의 프로젝트 귀속을 확인할 수 있다. 귀속이 모호한 기록을 임의로 확정하지 않는다.
- R01-E: 저장소에서 도구용 스킬/플러그인과 CLI를 설치하고 스킬에서 공통 초기화를 실행할 수 있다. 기존·신규 프로젝트에 같은 초기화 명령을 쓰며 도구별 별도 초기화 정책을 만들지 않는다.

#### R02. AI 도구 간 기록 연결과 수집 상태 (G0·P0)

외부 AI에서 생성한 기록을 읽고, 정리한 맥락을 다음 AI 작업에서 재사용한다.

- R02-A: Codex와 Claude Code에서 유래한 기록을 동일 프로젝트와 원본 근거에 연결하고 도구별 역할을 고정하지 않는다.
- R02-B: 과거 기록 가져오기와 진행 중인 기록 수집을 구별한다. 지원 범위·연결 상태·마지막 반영·실패를 확인할 수 있다.
- R02-C: 재수집·재시도·외부 편집을 처리해 중복과 변경 누락을 식별한다. 일부 수집만 성공한 결과를 전체 완료로 표시하지 않는다.
- R02-D: 한 도구의 기록을 다른 도구의 작업 맥락으로 조회할 수 있다. 공급자 세션 자체의 이전을 완료 조건으로 삼지 않는다.
- R02-E (신규): 사용자 요청과 함께 AI 답변도 분석 근거로 쓸 수 있다. AI가 요청을 어떻게 해석했고 사용자가 뒤이어 어떻게 정정했는지(‘그거 말고’)를 연결한다. 답변과 사용자 요청, 도구가 끼워 넣은 메시지를 구별해 표시한다. R11-B의 대화 결과 신호는 이 요구를 전제로 한다.
- R02-F (신규): 도구와 프로젝트를 연결한 뒤 수집·분석이 시작되기까지 사용자가 명령을 외우거나 반복 실행할 필요가 없다. 실제로 수집·분석이 동작 중인지, 꺼져 있거나 실패했는지 한곳에서 확인한다.

### G1 AI 활용 능력 성장

#### R11. 대화 중 모호한 요청 감지와 용어집 (G1·P0, 신규)

사용자가 용어나 배경지식 없이 넓게 요청한 지점을 대화 중에 잡아내 용어집으로 정리하고 알린다.

- R11-A: 연결된 도구에서 사용자 요청이 들어오면 별도 명령 없이 감지가 실행된다. 요청 직후 감지와 수집 후 감지를 구별하고 도구별 지원 차이를 표시한다. 감지가 실행되지 않은 요청을 감지 완료로 표시하지 않는다.
- R11-B: 요청을 먼저 단계(탐색·진단·실행·검증 등)로 나누고 그 단계에 맞는 기준만 적용한다. 탐색 단계의 짧고 넓은 요청을 실행 단계의 기준으로 평가하지 않는다. 후보는 두 종류의 신호로 찾는다.
  - 표현 신호: 고정 표현(‘잘’, ‘알아서’, ‘적당히’, ‘깔끔하게’, ‘예쁘게’), 영역명만 지정한 요청(예: ‘UI/UX 적용’, ‘최적화’, ‘보안 강화’), 기준 없는 평가어, 대상·범위·완료 조건이 빠진 요청.
  - 대화 결과 신호: 요청 뒤에 AI가 되물은 질문, 사용자의 정정(‘그거 말고’, ‘아니 내 말은’), 비슷한 요청의 재시도. 결과 신호는 사용자를 판정하지 않는 근거이므로 표현 신호보다 우선해 판단 이유로 보인다.
  - 공통: 후보마다 신호 종류, 판단 이유, 근거 원문을 남긴다. 한국어 위임 표현은 별도 사전으로 관리하고 사용자가 항목을 추가·제외할 수 있다.
- R11-C: 용어집은 후보와 확정 두 단계로 관리한다. 감지된 용어는 먼저 후보 원장에 근거를 쌓고, 사용자가 수락하거나 같은 용어의 근거가 정한 기준 이상 쌓였을 때 확정 항목으로 제안한다. 확정 항목은 용어, 한·영 별칭(최소 하나), 의미 후보, 사용 문맥(원문 ID), 정확한 개념과 레퍼런스, 더 구체적인 요청 예시, 관련 프로젝트, 상태를 가진다. 별칭으로 같은 용어를 묶어 중복 항목을 만들지 않는다.
- R11-D: 알림에서 요청 원문과 용어집 항목으로 바로 이동한다. 같은 원인·근거로 반복 알리지 않으며 알림 빈도와 조용한 시간을 설정할 수 있다. 알림은 판단 이유, 쓸 수 있는 용어, 더 구체적인 요청 예시로 구성하며, 모르는 사실은 지어내지 않고 사용자가 채울 빈칸으로 남긴다.
- R11-E: 사용자는 후보를 수락·수정·제외할 수 있다. 제외한 항목과 이유는 영구히 기억해 같은 근거로 다시 알리지 않고, 이유는 다음 감지·제안에 반영한다. 사용자가 제안된 용어와 예시를 직접 고칠 수 있다.
- R11-F: 로컬 규칙 감지와 외부 AI 판단을 구별한다. 외부 AI를 쓰면 실행 전에 전달 범위·실행 도구·예상 호출 수와 이용 한도 사용을 보여 주고 상한을 둘 수 있다.
- R11-G: 확정된 용어집을 다음 AI 작업의 맥락(스킬 지침·규칙 문서·프로젝트 안의 에이전트가 읽는 목록 문서 등)으로 내보낼 수 있다. 어느 도구·프로젝트에 넣을지는 사용자가 정하며 자동 주입을 기본으로 가정하지 않는다. 규칙 문서는 SiloLink가 표시한 블록만 고친다.
- R11-H (신규): 사용자는 요청을 ‘일부러 넓게 맡김’으로 표시할 수 있다. 표시는 기록되어 감지 후보와 성장 계산(R07-F)에서 불리하게 쓰이지 않으며, 대화 중에는 짧은 표시로도 지정할 수 있다.
- R11-I (신규): 대화 중 감지는 요청을 대체하거나 사용자 모르게 지시를 덧붙이지 않는다. 기록과 알림을 기본으로 하고, 맥락 주입은 R11-G에서 사용자가 켠 범위로 한정한다.

#### R07. 실제 문맥에 기반한 학습 가이드 (G1·P0)

자주 궁금해하거나 모호하게 사용한 용어를 모아 학습하고 다음 요청·작업에 적용하도록 돕는다.

- R07-A: 실제 요청 문맥, 정확한 개념과 레퍼런스, 개선된 요청 예시, 현재 프로젝트 적용 과제를 함께 제공할 수 있다.
- R07-B: 용어가 여러 의미로 해석되면 사용 문맥과 후보 의미를 구별하며, 사용자의 뜻을 확인하기 전에 하나로 확정하지 않는다.
- R07-C: 사용자가 학습 주제와 적용 과제를 열고 수정·보류·정리할 수 있다. 자료를 열었다는 사실만으로 이해 완료를 확정하지 않는다.
- R07-D: 후속 사용에서 개선 여부를 판단한다면 근거와 비교 기간을 보여준다. 자동화된 학습 판정의 상세 기준은 후속 검증 대상이다.
- R07-E (신규): 용어집 항목(R11)과 학습 주제를 연결해 같은 개념의 감지 근거·학습·적용 과제를 한곳에서 이어 본다.
- R07-F (신규): 요청을 프로젝트·주제별로 묶어 같은 주제의 이전·이후 요청을 나란히 보여 주고, 대상·범위·완료 조건이 구체화됐는지 근거 원문과 함께 표시한다. 추세·숙달·퇴보는 LLM 판정이 아니라 결정적 계산(예: 항목별 지수이동평균, 근거가 적을 때의 보수적 처리, 여러 기간에 걸쳐 유지될 때만 숙달)으로 낸다. 요청이 짧아졌다는 이유만으로 개선으로 판단하지 않고, 근거가 적으면 ‘아직 판단 불가’로 표시한다.
- R07-G (신규): 확정된 용어집 항목과 요청 예시를 간격 반복(예: 1·3·7·16일)으로 다시 보여 줄 수 있다. 복습은 사용자가 켜고 끄며, 알림 빈도 설정(R11-D)을 따른다.
- R07-H (신규): 더 나은 요청 예시는 일반 템플릿보다 같은 주제에서 사용자가 실제로 구체적으로 썼던 요청을 우선 사용한다. 그런 요청이 없을 때만 일반 예시를 쓰고 그 사실을 표시한다.

#### R03. 요청·선택 패턴과 지식 연결 분석 (G1·P0, G2)

반복 요청·모호한 용어·선택과 개선·중복 조사·프로젝트 간 관련 지식을 찾아 보여준다.

- R03-A: 분석 항목에서 관련 프로젝트·기록·시점·근거 위치와 분석 이유를 확인할 수 있다.
- R03-B: 반복된 실무 작업, 시안을 통한 기준 탐색, 이해 공백 후보를 구별해 설명하고 불확실한 판단은 추정으로 표시한다. 대안 선택·추가 개선·분기의 관계를 연결하고, 기록에 없는 선택 이유를 임의로 보충하지 않는다. 모든 사용에 시안 트리 작성을 강제하지 않는다.
- R03-C: 여러 프로젝트에 공통으로 고려할 내용과 적용 조건이 다른 내용을 함께 보여준다. 유사성만으로 원문·규칙을 자동 병합하지 않는다.
- R03-D: 사용자는 잘못된 해석·연결을 수정하거나 제외할 수 있다. 수정한 판단과 분석 대상 원문을 구별해 남긴다.
- R03-E: 데이터가 부족하거나 근거가 없을 때 개인화된 발견을 만들어내지 않고 부족한 범위를 표시한다.
- R03-F: 자주 요청한 주제·용어·반복 조사와 프로젝트별 분포를 기간·수집 범위·관련 원문과 함께 한눈에 살펴볼 수 있다. 확인한 기록의 빈도를 전체 사용 빈도로 단정하지 않는다.
- R03-G: 여러 대화·문서·프로젝트에 나뉜 개념과 판단 근거를 연결해, 함께 이해할 내용·다시 활용할 지식·다른 프로젝트에도 고려할 조건을 설명한다. 연결 제안을 이해 부족이나 학습 완료 판정으로 취급하지 않는다.
- R03-H: 프로젝트를 합치거나 일부를 분리하는 접근의 장단점·의존 관계·공통화할 요소·남길 차이를 기존 문서와 조사 근거로 비교할 수 있다. 구조 변경을 필수 절차로 강제하지 않으며 실제 저장소 변경과 구별한다.

### G2 지식 축적과 보고

#### R04. 레퍼런스 기반 조사와 의견 비교 (G2·P1)

기술·자료·아키텍처·정책 등의 조사에서 공식 자료를 필수로 확인하고, 주제에 따라 논문과 관련 커뮤니티 의견을 함께 검토한다.

- R04-A: 주장별 원문 링크·확인 시점·관련 버전·적용 조건을 확인할 수 있다. 공식·논문·커뮤니티·AI 해석을 구별한다.
- R04-B: 공식 자료를 확인하지 못하면 조사 근거가 불완전함을 표시한다. 검색 결과 제목이나 모델의 기억을 원문 확인으로 표시하지 않는다.
- R04-C: 의견이 엇갈리는 쟁점·찬반 이유·환경 차이를 한눈에 비교하고 현재 프로젝트에 적합한 이유와 미확인 사항을 볼 수 있다.
- R04-D: 사용자 기록을 근거로 새로운 접근을 조사하고 후속 질문을 이어갈 수 있다. 커뮤니티 다수 의견을 검증된 사실로 승격하지 않는다.
- R04-E: 구현 실험은 모든 조사에 강제하지 않는다. 아키텍처처럼 복합 조건을 판단하는 경우에도 유용한 비교·설명·추천을 제공한다.
- R04-F (신규): 새 질문이나 조사가 이미 조사·정리한 내용과 겹치면(“전에 조사한 적 있나?”) 기존 노트·출처·확인 시점을 먼저 알려 준다. 오래되어 다시 확인이 필요한 자료와 그대로 쓸 수 있는 자료를 구별하며, 재조사 여부는 사용자가 정한다.

#### R10. 문서·학습·일정의 지속 관리와 보고 (G2·P1)

프로젝트별 기술 문서·아키텍처·PRD·조사 리포트를 모아 읽고 관리하며 학습·일정·후속 작업과 보고 자료로 연결한다.

- R10-A: 문서의 프로젝트·주제·관련 결정과 원본을 찾아볼 수 있다. 문서가 부족한 상태도 표현하고 누락된 내용을 사실로 보충하지 않는다.
- R10-B: 사용자가 문서·대화·학습 항목을 후속 작업이나 일정과 연결할 수 있다. 자동 일정 배치·외부 캘린더 연동의 범위는 미정이다.
- R10-C: 사람이 읽고 공유할 기술 정리서를 만들 수 있다. 앱 설치 없이 읽을 결과물의 형식·공유 방식은 후속 결정이다.
- R10-D (신규): 노트·조사·결정·작업 실적에서 기간·프로젝트·주제를 골라 회사 보고용 기술 보고서로 추출한다. 확인된 사실, 검토한 분석, 검토하지 않은 추정을 구별하고 근거 원문으로 돌아갈 수 있다.

### G3 근거 있는 계획

#### R09. 작업 실적과 근거 있는 계획 (G3·P1)

기능과 설계·구현·검토·테스트 등 작업 관점의 실적을 다음 계획에 재사용한다.

- R09-A: 기능·작업·AI 세션의 관계를 연결하고 작업 단계의 반복·병렬 수행을 표현한다. 하나의 고정 단계 순서를 강제하지 않는다.
- R09-B: 본인 투입 시간·AI 실행 및 대기·전체 경과를 구별하고 측정 방식·기간·누락·추정을 표시한다. 겹치는 시간을 단순 합산하지 않는다.
- R09-C: 구현 종료와 사용자 테스트를 구별한다. 사용자 테스트 후 수락 또는 재작업을 기록해 실제 완료 판단과 소요 이력을 추적한다.
- R09-D: 계획에 참고 실적·유사성과 차이·작업 기준·가정·범위를 연결한다. 근거가 부족한 예상은 잠정 추정으로 표시한다.
- R09-E: 예상 수정 시 새 근거·조건 변경·작업 범위 변경을 확인할 수 있다. 데이터가 충분하지 않은 상태에서 예측 정확도 향상을 보장하지 않는다.
- R09-F (신규): AI 세션의 요청과 결과를 기능·작업 단위 후보로 묶어 실적으로 남길 수 있다. 기능·티켓 ID가 있으면 이를 묶음 기준으로 쓴다. 자동 묶음은 후보이며 사용자가 확인·수정한다. 기록에서 계산한 활동 시간은 계산 규칙(예: 일정 시간 넘는 공백 제외, 자정 경계 분할)을 함께 표시한다.
- R09-G (신규): 계획할 때 비교 실적의 건수·조건·중앙값·범위를 근거로 예상하고, 이전 실적에서 시간이 많이 든 구간과 단축할 수 있는 방법을 근거와 함께 제안한다. AI 도구가 계획을 세울 때도 이 실적을 맥락으로 받을 수 있다.

### G4 자동 일지와 회고

#### R06. 백그라운드 안내와 일간·주간 회고 (G4·P1)

의미 있는 패턴은 즉시 알리고, 사용자가 설정한 하루 마감 시각과 주간 단위로 회고 자료를 제공한다.

- R06-A: 패턴 발견 알림에서 발견 이유와 근거 분석으로 이동한다. 같은 원인·같은 근거의 알림이 매 수집마다 반복되지 않도록 식별한다.
- R06-B: 하루 마감 시각·적용 시간대·주간 회고 시점을 설정하고 해당 기간의 보고서를 확인한다.
- R06-C: 일간은 해당 기간의 활동·발견·후속 항목을, 주간은 기간 간 변화·반복 주제·프로젝트 공통점을 살펴볼 수 있게 한다.
- R06-D: 앱 실행·백그라운드 유지·종료 상태를 사용자가 이해할 수 있다. 종료 중 놓친 알림의 처리 방식과 보고서 대상 기간을 구별한다.
- R06-E: 알림을 잠시 미루거나 설정을 바꾸고도 생성된 보고서를 열 수 있다. 지연된 분석을 발생 당시의 즉시 분석으로 표시하지 않는다.
- R06-F (신규): 하루 마감 시각이 지나면 그날의 작업·요청·발견·완료 항목을 일지 문서로 자동 생성하고, 주 경계에 주간 일지로 묶는다. 세션이 끝날 때 정리한 결정·발견·남은 질문을 일지의 입력으로 쓸 수 있다. 앱이 꺼져 있던 기간은 다음 실행 때 대상 기간을 표시해 생성한다. 사용자가 일지를 고쳐도 원본 기록과 구별된다. 검토하지 않은 일간 후보는 주간 일지에서 확인된 사실로 승격하지 않는다.

첫 구현의 종료 상태 처리 제안: 백그라운드 실행 중에 분석·알림을 수행하고, 완전히 종료한 동안의 누락은 다음 실행 시 대상 기간을 표시해 보완한다. OS 서비스나 앱 종료 중 상시 실행은 기술 결정 전이다.

### G5 규칙 전파

#### R08. 공통·로컬 규칙과 실제 문서 개선 (G5·P2)

컨벤션·하네스 규칙·문서 관리·프로젝트 정책을 비교하고 공통화·분리·예외를 검토하며 선택한 프로젝트에 반영한다.

- R08-A: 공통 규칙·로컬 규칙·적용 대상과 차이를 한눈에 확인한다. 서로 충돌하거나 적용 조건이 다른 규칙을 표시한다.
- R08-B: 공통화·분리 제안에 반복 근거, 프로젝트별 영향과 유지할 차이를 연결한다. 유사한 규칙을 모두 같은 규칙으로 처리하지 않는다.
- R08-C: 사용자가 AI와 제안을 다듬고 적용 대상을 선택하면 실제 변경 내용과 결과를 확인할 수 있다. 제안 열람을 변경 확정으로 취급하지 않는다.
- R08-D: 변경안을 만든 뒤 원본이 바뀌면 충돌을 드러낸다. 미선택 프로젝트를 변경하지 않으며, 일부 프로젝트만 적용되면 실제 상태와 실패·재시도 대상을 구별한다.
- R08-E: 적용 이력과 복구에 필요한 이전 내용을 연결한다. 정확한 규칙 상속·우선순위·저장 형식·다중 프로젝트 반영 방식은 기술 설계에서 정한다.
- R08-F (신규): 한 프로젝트에 규칙이 추가·수정되면 다른 프로젝트에 적용할 후보로 알리고 차이와 예상 영향을 보여 준다. 대화에서 같은 지시·정정이 반복되면(예: 두 번 이상) 이를 규칙 후보로 제안할 수 있다. 실제 반영은 사용자가 대상을 고른 경우에만 하며, 규칙 문서는 SiloLink가 표시한 블록만 고친다.

### 공통 창구

#### R05. 문서·프로젝트 맥락을 활용하는 데스크톱 채팅 (P2)

문서·보고서·규칙·여러 프로젝트를 보면서 자유롭게 질문하고 조사·분석·개선으로 이어간다.

- R05-A: 사용 중인 프로젝트·문서·분석 근거를 확인하고 질문에 포함할 범위를 조정할 수 있다. 프로젝트 간 비교도 명시한 범위에서 가능하다.
- R05-B: 작업에 사용할 AI 도구를 선택하고 설계·구현·검토 같은 역할을 상황에 맞게 바꿀 수 있다.
- R05-C: 실행 중·추가 입력 대기·실패·취소·완료를 구별한다. 중단·실패한 대화의 원문과 이미 생성된 결과를 확인할 수 있다.
- R05-D: 대화 결과를 기록·학습 주제·규칙이나 변경 제안으로 이어가고 근거 대화로 돌아갈 수 있다. 자유로운 질문에 미리 정한 양식을 강제하지 않는다.

- 연결부별 기능 차이를 드러내고 지원하지 않는 기능을 성공으로 표시하지 않는다.

정확한 스키마·폴더 규격·공통 규칙의 저장 위치·분석 실행 주기·성능 및 비용 한도는 아직 확정하지 않는다.

## 11. 개발 순서 제안

사용자에게 제공할 절차를 고정하는 것이 아니라, 가장 큰 목적부터 실제 가치를 확인하기 위한 개발 측 순서다. v0.1의 0~1단계(수집·실행 기술 검증, 프로젝트·기록 기반)는 대부분 구현됐으며 남은 항목은 9절에 있다. 1~3단계는 [LLM Wiki 계열 조사](../research/llm-wiki.md)에서 확인한 범위에서 기존 도구가 하지 않는 부분이며, 이미 수집한 기록으로 모델 호출 없이 시작할 수 있는 순서로 배치했다.

| 5. 자동 일지 | 세션 끝 정리를 입력으로 일간·주간 일지 문서 자동 생성과 누락 기간 보완 | R06-F | 마감 시각 경계·재실행·꺼진 기간에서 중복·누락 없이 생성됨 |

### 요구 기반 사례

| 사례 | 기대하는 관찰 |

| 의도적으로 넓게 맡긴 탐색 요청 | 탐색 단계로 분류되거나 ‘일부러 넓게 맡김’ 표시가 남고, 후보·성장 계산에서 불리하게 쓰이지 않음 |

| 같은 용어를 한국어·영어로 섞어 쓴 요청 | 별칭으로 한 용어집 항목에 묶이고 중복 항목이 생기지 않음 |

| 용어 학습 후 같은 주제의 다음 요청 | 이전·이후 원문을 나란히 보여 주고 구체화 여부를 결정적 계산과 근거로 설명. 근거가 적으면 판단 불가 |
| 대화 중 감지가 켜진 상태의 요청 | 요청 원문이 바뀌거나 사용자 모르게 지시가 추가되지 않고, 기록과 알림만 남음 |
| 정리된 docs, 흩어진 Markdown, 채팅 중심 프로젝트 연결 | 수집 범위와 누락을 구별하고 원본과 프로젝트 귀속을 보존 |
| 같은 기록 재수집·초기화 재실행·다른 도구로 이어가기 | 중복 없이 같은 근거를 조회하며 공급자별 차이를 확인 |
| 이미 조사한 주제를 다시 질문 | 기존 노트·출처·확인 시점을 먼저 보여 주고 재조사 여부를 사용자가 정함 |
| 공식·논문·커뮤니티 의견 충돌과 자료 접근 실패 | 출처·조건별 차이와 미확인 범위를 확인하고 후속 판단 가능 |
| 마감 시각 변경·앱이 꺼진 날·주 경계 | 일지가 중복·누락 없이 생성되고 보완한 기간을 표시 |
| 두 프로젝트에 규칙 적용 중 한쪽 외부 편집·실패 | 미선택 대상 보존, 충돌과 실제 반영 상태 확인, 재시도·복구 가능 |
| 사람 작업과 AI 실행이 겹치고 사용자 테스트 후 재작업 | 시간 합산 오류 없이 완료 판단·예상 변경 근거를 추적 |

입문자는 자신의 요청 문맥에서 용어·요청 개선 가이드를 받고 다음 요청으로 적용하는 흐름을 확인한다. 개인 개발자는 여러 프로젝트의 분석에서 공통 규칙을 다듬어 선택한 프로젝트에 반영하고, 실적으로 계획하는 흐름을 확인한다. 두 경우 모두 화면·작업 순서는 바꿔서 검증한다.

초기 CLI 검증 명령은 `cargo test --all-targets --locked`이며 [테스트 사례 목록](../../tests/CASE_MATRIX.md)에서 구현·검증 범위와 남은 작업을 확인한다. 새 동작은 요구 기반 실패를 먼저 확인한 뒤 구현·통합 검증한다. 마지막 제품 완료 판단에는 실제 Windows 환경에서 사용자가 직접 테스트한 결과를 포함한다. CLI 테스트나 검증용 공급자 응답만으로 데스크톱·분석 경험과 실제 모델 품질까지 검증했다고 판단하지 않는다.

### 효과를 판단할 관찰 항목

- 감지 후보 중 사용자가 타당하다고 본 항목과 수정·제외한 이유.
- 같은 주제 요청에서 대상·범위·완료 조건이 구체화된 사례와 그렇지 않은 사례.
- 용어집 항목의 재방문·다음 작업 맥락으로의 재사용.
- 기존 기록이 다음 작업에 재사용된 사례와 다시 조사하게 된 이유.
- 일지·보고서를 실제 보고나 회고에 사용한 사례와 고쳐 쓴 부분.
- 계획의 예상과 실제 차이, 비교 가능한 실적 수·조건·시간 기록의 완전성.
- 규칙·문서 변경의 수동 정리 부담, 충돌·복구와 자발적인 반복 사용.

절감률·정확도·감지 정밀도·알림 수용률 같은 목표 수치는 아직 측정 근거가 없어 설정하지 않는다. 기준선과 평가 자료를 확보한 뒤 조정한다.

2026-11-08: 사용자가 SiloLink를 ‘연결만 하면 뒤에서 나를 파악해 돕는 AI 작업 비서’로 설명하고, 가장 큰 목적을 ‘잘 해줘라고 부탁하던 나의 AI 활용 능력 성장’으로 밝혔다. 대화 중 넓은 요청을 감지해 CLI로 용어집을 만들고 알리는 흐름을 테스트 중이라고 했다. 이를 기준으로 PRD를 v0.2로 재구성하고 v0.1을 구버전 기록으로 보존했다. 0.3.1 코드와 대조한 결과 기반·문서 변경·규칙 비교는 탄탄하지만 성장 루프(R11·R07)가 가장 약해 다음 개발의 중심으로 제안한다. 우선순위 배치와 개발 순서는 제안이며 사용자 확인 전이다.

2026-11-08: [LLM Wiki 계열 조사](../research/llm-wiki.md)를 반영했다. 사용자 요청에 따라 조사에서 얻은 관점을 요구와 개발 순서에 넣었다. 5절에 점수·등급 미표시, 요청을 바꾸지 않는 개입, 근거 표시 4종을 원칙으로 추가했다. R11에 요청 단계 분류와 대화 결과 신호(AI의 되물음·정정·재시도), 후보→확정 용어집과 한·영 별칭, 제외 이유 기억, ‘일부러 넓게 맡김’ 표시(R11-H), 요청 비대체(R11-I)를 넣었다. R07에 결정적 성장 계산, 간격 반복, 사용자 자신의 요청 예시(R07-G·H)를 넣었다. 개발 순서는 감지 기반→용어집→성장 측정→대화 중 트리거 순으로 바꿨다. 참고한 저장소의 기능은 README 기준이며 실행 검증하지 않았다. 세부 수치(복습 간격, 반복 횟수, 계산 계수)는 예시이며 13절에서 정한다.
