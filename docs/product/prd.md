## 1. 제품과 해결할 문제

SiloLink(사일로링크)는 여러 프로젝트와 AI 도구에 흩어진 기록을 연결하고, 사용자의 실제 작업 맥락을 바탕으로 AI 활용·조사·학습·프로젝트 운영을 지속적으로 지원한다. 이름은 도구별 정보 사일로를 연결한다는 의미다.

사용자는 다음 문제를 설명했다.

- 원하는 결과가 막연해 ‘잘해줘’, ‘그거 말고’를 반복하고, 결과나 시안을 본 뒤 자신의 기준을 발견한다.
- 같은 내용을 다시 조사하고, 한 프로젝트에서 얻은 지식이 다른 프로젝트에도 유효한지 알아차리기 어렵다.
- 기록이 채팅·정리된 `docs/`·흩어진 Markdown에 나뉘고 정리 수준도 다르다.
- 컨벤션·문서 관리·정책의 공통점과 차이를 비교하고 공통 규칙과 로컬 규칙을 운영하기 어렵다.
- AI의 ‘3일’, ‘5일’ 같은 예상이 누구의 기준인지 불분명하고 질문마다 달라진다.

사용자는 시안을 선택하고 개선안을 분기·비교하기도 하며, 선택 이유를 길게 설명할 때와 선택만 남길 때가 모두 있다. AI 도구의 역할도 상황에 따라 바뀐다. 제품은 이런 다양성을 지원한다.

## 2. 대상 사용자와 기대 효과

| 대상 | 기대하는 지원 |
| --- | --- |
| 여러 사이드 프로젝트를 운영하는 개인 개발자 | 기록 재사용, 공통·로컬 규칙과 문서 비교, 여러 프로젝트의 업무 파악 |
| 바이브 코딩을 시작하는 사용자 | 실제 요청 패턴에 맞춘 가이드, 용어 학습, 요청 개선과 근거 있는 의사결정 |
| 후속 확장 대상인 개발팀 | 여러 저장소의 규칙·문서와 지식을 공유하는 플랫폼 |

인터뷰 사용자는 Codex·Claude Code를 주력, Antigravity를 보조로 사용한다. 설계·구현·검토·테스트를 도구별로 고정하지 않으며, 한 도구의 결과를 다른 도구로 검토하기도 한다.

성공은 더 구체적인 요청, 중복 조사 감소, 프로젝트 관리 부담 감소, 회고·학습과 새로운 접근의 발견, 실제 이력에 근거한 계획, 업무 핵심의 빠른 파악으로 판단한다. 정량적 개선 목표는 사용 기준선을 확보한 뒤 정한다. 기존 유사 제품은 인터뷰 당시 사용해 보지 않았고 경쟁 제품 대비 효과·수요·전환 의향은 검증 전이다.

## 3. 원칙과 결정 상태

### 범용 지원 원칙

분석·조사·학습·규칙 관리·플래닝은 상황에 따라 활용하는 능력이다. 사용자의 요청 문법, 작업 순서, AI 역할, 결과 표현을 단일 절차로 고정하지 않는다. 시안 트리·비교표·보고서·설계 단계는 사용 가능한 표현과 예시다.

근거와 판단 상태를 드러내고 사용자의 의사결정을 돕는다. 반복 요청·부실한 기록·짧은 선택 표현을 지식 부족으로 확정하지 않는다. 기록으로 확인한 사실과 분석상 추정, 아이디어·제안·결정·구현·검증 상태를 구별한다.

로컬 저장과 외부 AI로 전달하는 데이터는 별도 범위다. 전체 기록의 완전한 자동 수집, 완전 오프라인, 공급자별 동일 기능은 검증된 전제가 아니다.

Claude의 [공식 제품 제공·인증 조건](https://code.claude.com/docs/en/legal-and-compliance)은 사용자가 미수정 CLI에 자기 구독으로 로그인하는 호스팅과 제3자 자체 로그인·토큰 중계를 구별한다. [연동 조사](../research/cli-integration.md)의 공식 문서·Orca 등 구현 사례·실제 검증을 기준으로 로컬 CLI 방식을 설계한다. 기존 구독 활용 목표에 맞춰 진행하며 API 인증은 공식 CLI의 선택지로 유지한다.

## 4. 첫 사용과 지속 사용

사용자가 설명한 시작점은 기존 프로젝트들에 `silolink init`을 실행하고, 과거 문서를 관리 구성으로 재구조화해 싱크업한 뒤 데스크톱에서 살펴보는 것이다.

2026-11-02 추가 결정: 사용자는 CLI와 Codex·Claude Code·Antigravity 등의 스킬/플러그인을 설치하고, 각 도구 안에서 `/silolink init` 같은 호출이나 자연어 요청으로 CLI를 실행한다. 기존 프로젝트와 새 프로젝트의 초기화 진입점을 구분하지 않는다. 독립 스킬 설치와 Codex용 로컬 플러그인 체험 배포를 제공하며, Codex는 공식 스킬 메뉴/`$silolink init`, Claude Code·Antigravity는 지원 화면의 `/silolink init`에 연결한다. 호출 표기는 도구가 지원하는 문법을 따른다. 앱에서는 폴더 선택과 연결 버튼으로 같은 초기화를 실행한다.

이후에는 평소 AI 도구를 쓰는 동안 기록이 쌓이고, 백그라운드 데스크톱이 패턴·용어·개선점을 발견해 알려준다. 사용자는 문서·보고서를 읽고 자유롭게 채팅·추가 조사·학습·규칙 개선을 이어간다. 타당한 제안은 AI와 다듬어 선택한 프로젝트의 실제 변경으로 반영한다.

이 설명은 연결되어야 할 경험이며 반드시 거쳐야 하는 화면 순서가 아니다. 사용자는 문서·대화·분석·프로젝트 등 필요한 지점에서 시작할 수 있다.

## 5. 기능 요구와 수용 기준

### 첫 설치 관점의 개선 기준 — 2026-11-02

이번 검토의 페르소나는 ‘개발 지식이 없고 바이브 코딩에 관심이 생겼으며, 문서 관리와 AI 활용에 도움이 된다고 듣고 처음 설치하려는 사람’이다. 설치 설명에서 CLI·스킬·init의 차이를 먼저 배우게 하지 않는다. 이 페르소나는 기존 개인 개발자 대상을 대체하지 않으며 첫 진입의 기준으로 추가한다.

| P1 | ‘AI를 더 똑똑하게’라는 기대가 모델 학습·도구 전체 자동 공유로 해석될 수 있음 | 지원 문서 형식·첫 결과·다음 행동과 맥락 활용 방식을 사용자 안내와 공통 스킬에 명시. 모델 자동 학습이나 모든 도구에 대한 자동 주입으로 설명하지 않음 |
| P2 | AI 도구 미설치·로그인 실패 시 개발 용어와 일반 오류 안내에 의존 | 사용자용 복구 안내 추가. 앱에서 공급자별 설치·로그인 준비 상태를 직접 확인하고 안내하는 흐름은 후속 개선 |

첫 수용 기준은 ‘명령어를 입력하지 않고 제공받은 패키지를 등록하고 Codex 설치 목록에서 발견할 수 있으며, 앱에서는 폴더 선택과 연결만으로 실제 문서의 첫 결과에 도달한다’이다. 지원하지 않는 파일, 읽기 실패, 기록 미수집과 공개 배포 미완료를 성공으로 표시하지 않는다. 실제 비개발자 수락 테스트와 공개 배포의 완료 여부는 구현·자동 검증과 별도로 기록한다.

설치 후 연결의 추가 기준: 앱의 세 도구 연결 버튼은 실제 사용자 스킬 파일을 만들고, 메타데이터가 가리키는 동봉 실행 파일로 초기화·문서 조회가 동작해야 한다. 등록 상태 확인은 무수정이며, 수정된 스킬·다른 설치·링크는 보존한다. 지원하지 않는 호스트나 임의 실행 파일 경로를 화면에서 등록할 수 없어야 한다. ‘연결됨’은 스킬 등록의 상태이며 호스트 설치·로그인이나 실제 모델 실행의 성공을 뜻하지 않는다.

기능 발견의 추가 기준: 사용자가 `init` 같은 CLI 하위 명령을 외우지 않아도 스킬 목록에서 프로젝트 연결·문서 확인·기록 가져오기·변경안 검토/적용/이력/복구 등을 각각 선택한다. 통합 `silolink`를 유지하면서 `silolink-init` 등 기능별 진입점 10개와 한국어 이름·설명·기본 요청을 함께 설치한다. 앱의 기존 단일 스킬 설치에는 기존 파일을 보존하는 추가 업데이트를 제공하고, 플러그인 ZIP도 같은 목록을 제공한다.

배포의 추가 기준: PR·main 검증과 태그 게시의 권한을 구별하며 검사·앱 UI 검증에 실패한 결과를 공개하지 않는다. 태그와 앱·CLI·프런트엔드·플러그인 버전이 일치해야 하고, 설치 EXE·플러그인 ZIP·체크섬을 전달한다. 게시 중 실패는 초안으로 보존하고 이미 공개한 릴리스는 자동 덮어쓰지 않는다.

### 기존 기능 요구

아래 요구의 목적은 인터뷰에 근거한다. 상세 수용 기준은 구현·사용자 검증을 위한 제안이다. ‘첫 검증’은 7절의 초기 개발 범위를 뜻하며 전체 제품의 완료를 뜻하지 않는다.

### R01. 프로젝트 연결과 기존 문서 싱크업

프로젝트를 초기화하고 채팅·문서 등 서로 다른 상태의 과거 기록을 연결하며 문서 구성을 정돈한다.

- R01-A: 기존 문서·흩어진 Markdown·문서 없는 프로젝트를 각각 연결할 수 있고, 수집한 것·수집하지 못한 것·판단이 필요한 것을 확인할 수 있다.
- R01-B: 초기화 재실행으로 프로젝트나 기록이 중복되지 않고 기존 내용이 조용히 덮어써지지 않는다.
- R01-C: 재구조화 제안은 이동·통합·재작성·삭제와 관련 링크 영향을 보여준다. 적용 후 실제 파일과 링크가 일치하고, 변경 전 상태와 적용 결과를 추적할 수 있다.
- R01-D: 같은 폴더명·여러 경로·워크트리의 프로젝트 귀속을 확인할 수 있다. 귀속이 모호한 기록을 임의로 확정하지 않는다.
- R01-E: 저장소에서 도구용 스킬/플러그인과 CLI를 설치하고 스킬에서 공통 초기화를 실행할 수 있다. 기존·신규 프로젝트에 같은 초기화 명령을 쓰며 도구별 별도 초기화 정책을 만들지 않는다.

### R02. AI 도구 간 기록 연결과 수집 상태

외부 AI에서 생성한 기록을 데스크톱에서 읽고, 데스크톱에서 정리한 맥락을 다음 AI 작업에서 재사용한다.

- R02-A: Codex와 Claude Code에서 유래한 기록을 동일 프로젝트와 원본 근거에 연결하고 도구별 역할을 고정하지 않는다.
- R02-B: 과거 기록 가져오기와 진행 중인 기록 수집을 구별한다. 지원 범위·연결 상태·마지막 반영·실패를 확인할 수 있다.
- R02-C: 재수집·재시도·외부 편집을 처리해 중복과 변경 누락을 식별한다. 일부 수집만 성공한 결과를 전체 완료로 표시하지 않는다.
- R02-D: 한 도구의 기록을 다른 도구의 작업 맥락으로 조회할 수 있다. 공급자 세션 자체의 이전을 완료 조건으로 삼지 않는다.

### R03. 요청·선택 패턴과 지식 연결 분석

반복 요청·모호한 용어·선택과 개선·중복 조사·프로젝트 간 관련 지식을 찾아 보여준다.

- R03-A: 분석 항목에서 관련 프로젝트·기록·시점·근거 위치와 분석 이유를 확인할 수 있다.
- R03-B: 반복된 실무 작업, 시안을 통한 기준 탐색, 이해 공백 후보를 구별해 설명하고 불확실한 판단은 추정으로 표시한다. 대안 선택·추가 개선·분기의 관계를 연결하고, 기록에 없는 선택 이유를 임의로 보충하지 않는다. 모든 사용에 시안 트리 작성을 강제하지 않는다.
- R03-C: 여러 프로젝트에 공통으로 고려할 내용과 적용 조건이 다른 내용을 함께 보여준다. 유사성만으로 원문·규칙을 자동 병합하지 않는다.
- R03-D: 사용자는 잘못된 해석·연결을 수정하거나 제외할 수 있다. 수정한 판단과 분석 대상 원문을 구별해 남긴다.
- R03-E: 데이터가 부족하거나 근거가 없을 때 개인화된 발견을 만들어내지 않고 부족한 범위를 표시한다.
- R03-F: 자주 요청한 주제·용어·반복 조사와 프로젝트별 분포를 기간·수집 범위·관련 원문과 함께 한눈에 살펴볼 수 있다. 확인한 기록의 빈도를 전체 사용 빈도로 단정하지 않는다.
- R03-G: 여러 대화·문서·프로젝트에 나뉜 개념과 판단 근거를 연결해, 함께 이해할 내용·다시 활용할 지식·다른 프로젝트에도 고려할 조건을 설명한다. 연결 제안을 이해 부족이나 학습 완료 판정으로 취급하지 않는다.
- R03-H: 프로젝트를 합치거나 일부를 분리하는 접근의 장단점·의존 관계·공통화할 요소·남길 차이를 기존 문서와 조사 근거로 비교할 수 있다. 구조 변경을 조사 과정의 필수 절차로 강제하지 않으며 실제 저장소 변경과 구별한다.

### R04. 레퍼런스 기반 조사와 의견 비교

기술·자료·아키텍처·정책 등의 조사에서 공식 자료를 필수로 확인하고, 주제에 따라 논문과 관련 커뮤니티 의견을 함께 검토한다.

- R04-A: 주장별 원문 링크·확인 시점·관련 버전·적용 조건을 확인할 수 있다. 공식·논문·커뮤니티·AI 해석을 구별한다.
- R04-B: 공식 자료를 확인하지 못하면 조사 근거가 불완전함을 표시한다. 검색 결과 제목이나 모델의 기억을 원문 확인으로 표시하지 않는다.
- R04-C: 의견이 엇갈리는 쟁점·찬반 이유·환경 차이를 한눈에 비교하고 현재 프로젝트에 적합한 이유와 미확인 사항을 볼 수 있다.
- R04-D: 사용자 기록을 근거로 새로운 접근을 조사하고 후속 질문을 이어갈 수 있다. 커뮤니티 다수 의견을 검증된 사실로 승격하지 않는다.
- R04-E: 구현 실험은 모든 조사에 강제하지 않는다. 아키텍처처럼 복합 조건을 판단하는 경우에도 유용한 비교·설명·추천을 제공한다.

### R05. 문서·프로젝트 맥락을 활용하는 데스크톱 채팅

문서·보고서·규칙·여러 프로젝트를 보면서 자유롭게 질문하고 조사·분석·개선으로 이어간다.

- R05-A: 사용 중인 프로젝트·문서·분석 근거를 확인하고 질문에 포함할 범위를 조정할 수 있다. 프로젝트 간 비교도 명시한 범위에서 가능하다.
- R05-B: 작업에 사용할 AI 도구를 선택하고 설계·구현·검토 같은 역할을 상황에 맞게 바꿀 수 있다.
- R05-C: 실행 중·추가 입력 대기·실패·취소·완료를 구별한다. 중단·실패한 대화의 원문과 이미 생성된 결과를 확인할 수 있다.
- R05-D: 대화 결과를 기록·학습 주제·규칙이나 변경 제안으로 이어가고 근거 대화로 돌아갈 수 있다. 자유로운 질문에 미리 정한 양식을 강제하지 않는다.

### R06. 백그라운드 안내와 일간·주간 회고

의미 있는 패턴은 즉시 알리고, 사용자가 설정한 하루 마감 시각과 주간 단위로 회고 자료를 제공한다.

- R06-A: 패턴 발견 알림에서 발견 이유와 근거 분석으로 이동한다. 같은 원인·같은 근거의 알림이 매 수집마다 반복되지 않도록 식별한다.
- R06-B: 하루 마감 시각·적용 시간대·주간 회고 시점을 설정하고 해당 기간의 보고서를 확인한다. 주간 시점의 기본값은 아직 미정이다.
- R06-C: 일간은 해당 기간의 활동·발견·후속 항목을, 주간은 기간 간 변화·반복 주제·프로젝트 공통점을 살펴볼 수 있게 한다.
- R06-D: 앱 실행·백그라운드 유지·종료 상태를 사용자가 이해할 수 있다. 종료 중 놓친 알림의 처리 방식과 보고서 대상 기간을 구별한다.
- R06-E: 알림을 잠시 미루거나 설정을 바꾸고도 생성된 보고서를 열 수 있다. 지연된 분석을 발생 당시의 즉시 분석으로 표시하지 않는다.

첫 구현의 종료 상태 처리 제안: 백그라운드 실행 중에 분석·알림을 수행하고, 완전히 종료한 동안의 누락은 다음 실행 시 대상 기간을 표시해 보완한다. OS 서비스나 앱 종료 중 상시 실행은 기술 결정 전이다.

### R07. 실제 문맥에 기반한 학습 가이드

자주 궁금해하거나 모호하게 사용한 용어를 모아 학습하고 다음 요청·작업에 적용하도록 돕는다.

- R07-A: 실제 요청 문맥, 정확한 개념과 레퍼런스, 개선된 요청 예시, 현재 프로젝트 적용 과제를 함께 제공할 수 있다.
- R07-B: 용어가 여러 의미로 해석되면 사용 문맥과 후보 의미를 구별하며, 사용자의 뜻을 확인하기 전에 하나로 확정하지 않는다.
- R07-C: 사용자가 학습 주제와 적용 과제를 열고 수정·보류·정리할 수 있다. 자료를 열었다는 사실만으로 이해 완료를 확정하지 않는다.
- R07-D: 후속 사용에서 개선 여부를 판단한다면 근거와 비교 기간을 보여준다. 자동화된 학습 판정의 상세 기준은 후속 검증 대상이다.

### R08. 공통·로컬 규칙과 실제 문서 개선

컨벤션·문서 관리·프로젝트 정책을 비교하고 공통화·분리·예외를 검토하며 선택한 프로젝트에 반영한다.

- R08-A: 공통 규칙·로컬 규칙·적용 대상과 차이를 한눈에 확인한다. 서로 충돌하거나 적용 조건이 다른 규칙을 표시한다.
- R08-B: 공통화·분리 제안에 반복 근거, 프로젝트별 영향과 유지할 차이를 연결한다. 유사한 규칙을 모두 같은 규칙으로 처리하지 않는다.
- R08-C: 사용자가 AI와 제안을 다듬고 적용 대상을 선택하면 실제 변경 내용과 결과를 확인할 수 있다. 제안 열람을 변경 확정으로 취급하지 않는다.
- R08-D: 변경안을 만든 뒤 원본이 바뀌면 충돌을 드러낸다. 미선택 프로젝트를 변경하지 않으며, 일부 프로젝트만 적용되면 실제 상태와 실패·재시도 대상을 구별한다.
- R08-E: 적용 이력과 복구에 필요한 이전 내용을 연결한다. 정확한 규칙 상속·우선순위·저장 형식·다중 프로젝트 반영 방식은 기술 설계에서 정한다.

### R09. 작업 실적과 근거 있는 계획

기능과 설계·구현·검토·테스트 등 작업 관점의 실적을 신규 프로젝트 계획에 재사용한다.

- R09-A: 기능·작업·AI 세션의 관계를 연결하고 작업 단계의 반복·병렬 수행을 표현한다. 하나의 고정 단계 순서를 강제하지 않는다.
- R09-B: 본인 투입 시간·AI 실행 및 대기·전체 경과를 구별하고 측정 방식·기간·누락·추정을 표시한다. 겹치는 시간을 단순 합산하지 않는다.
- R09-C: 구현 종료와 사용자 테스트를 구별한다. 사용자 테스트 후 수락 또는 재작업을 기록해 실제 완료 판단과 소요 이력을 추적한다.
- R09-D: 계획에 참고 실적·유사성과 차이·작업 기준·가정·범위를 연결한다. 근거가 부족한 예상은 잠정 추정으로 표시한다.
- R09-E: 예상 수정 시 새 근거·조건 변경·작업 범위 변경을 확인할 수 있다. 데이터가 충분하지 않은 상태에서 예측 정확도 향상을 보장하지 않는다.

### R10. 문서·학습·일정의 지속 관리와 공유

프로젝트별 기술 문서·아키텍처·PRD·조사 리포트를 모아 읽고 관리하며 학습·일정·후속 작업으로 연결한다.

- R10-A: 문서의 프로젝트·주제·관련 결정과 원본을 찾아볼 수 있다. 문서가 부족한 상태도 표현하고 누락된 내용을 사실로 보충하지 않는다.
- R10-B: 사용자가 문서·대화·학습 항목을 후속 작업이나 일정과 연결할 수 있다. 자동 일정 배치·외부 캘린더 연동의 범위는 미정이다.
- R10-C: 사람이 읽고 공유할 기술 정리서를 만들 수 있다. 앱 설치 없이 읽을 결과물의 형식·공유 방식은 후속 결정이다.

| 문서·결정·규칙 | 관련 기록, 적용 대상·조건, 제안·검토·확정 상태, 변경 이력 |
| 분석·가이드·보고서 | 대상 기간·프로젝트, 원본 근거, 해석·추정·후속 제안 |
| AI 실행 | 도구·세션·진행·입력 대기·종료·오류·부분 결과 |

- 수집 대상은 연결된 프로젝트와 사용자가 선택한 맥락을 기준으로 설계한다. 기록 귀속·반영 여부가 불분명하면 숨기지 않는다.
- 자료의 지시문과 사용자 작업 지침을 구별하고, 인증정보를 기록물로 복사하지 않는다.
- 외부 AI에 전달할 맥락과 원본 저장 위치를 구별하고 수집·분석·변경 범위를 확인할 수 있게 한다.
- 장기 실행의 취소·실패·부분 결과와 외부 편집·동시 변경·복구를 관찰할 수 있어야 한다.
- 연결부별 기능 차이를 드러내고 지원하지 않는 기능을 성공으로 표시하지 않는다.

정확한 스키마·폴더 규격·공통 규칙의 저장 위치·분석 실행 주기·성능 및 비용 한도는 아직 확정하지 않는다.

## 7. 초기 개발 범위와 순서 제안

사용자에게 제공할 절차를 고정하는 것이 아니라 개발 측에서 불확실성을 줄이며 연결된 가치를 확인하는 순서다. 초기 범위 축소는 각 요구의 후속 확장을 열어둔다.

| 단계 | 제공하거나 검증할 결과 | 관련 요구 | 다음 단계로 이어갈 기준 |
| --- | --- | --- | --- |
| 0. 수집·실행 기술 검증 | Windows의 Codex·Claude Code에서 과거·진행 기록 접근, 프로젝트 귀속, 실행·이벤트·취소의 실제 지원 범위 확인 | R02, R05, R09 | 지원·미지원과 실측 근거를 기록하고, 최소 연결 방법·인증 범위·저장 요구를 설명할 수 있음 |
| 1. 프로젝트·기록 기반 | 공통 CLI·두 도구 연결·초기화·기록 가져오기, 최소 데스크톱의 프로젝트·문서 조회와 정리 제안 | R01, R02, R10 | 서로 다른 상태의 기존 프로젝트를 연결하고 두 도구의 기록을 원본 근거와 함께 조회·재사용함 |
| 2. 분석·조사·학습·채팅 | 반복·모호성·프로젝트 간 연결 분석, 출처 비교, 맥락 채팅과 실제 문맥의 학습 가이드 | R03, R04, R05, R07 | 근거에서 분석을 검토하고 자유롭게 질문·조사·학습을 이어가며 불확실한 결과를 수정할 수 있음 |
| 3. 지속 안내와 실제 개선 | 즉시·일간·주간 안내, 공통·로컬 규칙 비교와 선택한 프로젝트의 문서 변경 | R06, R08 | 알림에서 근거와 후속 작업으로 이어가고, 변경·충돌·부분 실패·복구를 확인함 |
| 4. 실적 기반 계획 확장 | 축적한 작업·시간·사용자 테스트 이력으로 계획과 예상 차이 설명 | R09 | 수집 가능한 시간과 추정을 구분하고 유사 실적을 다음 계획의 근거로 연결함 |

첫 연결 검증은 1~3단계의 좁은 흐름을 대상으로 한다. 최소 문서 조회만으로 제품 가치 검증을 완료했다고 판단하지 않는다. 공식 레퍼런스 조사와 AI 활용 개선은 초기 검증에 포함한다. 실적 데이터의 기본 식별·시점·완료 기록은 1단계부터 고려하되, 정밀한 개인 활동 측정과 예측 보정은 실제 수집 결과에 맞춰 확장한다.

0단계 현재 결과: 두 도구의 공식 인터페이스로 과거 기록을 읽었고, 기존 로그인 환경에서 실제 응답·스트리밍·생성 중 취소를 확인했다. 두 도구의 취소 결과 표현은 서로 다르다. 외부 CLI의 자동 수집·승인 대기·도구 실행·재시도·복구는 검증 전이며 0단계 전체 완료로 표시하지 않는다. 상세 근거는 연동 조사의 V01~V10이다.

1단계 현재 구현: 세 도구용 독립 스킬 설치·공통 CLI 초기화와 과거 텍스트 이력 조회·명시적 로컬 저장·전경 주기 수집을 연결했다. 프로젝트 귀속·원문 ID·복사 이력·시간 근거·중복·페이지·부분 실패·revision·강제 종료 후 저장 복구를 다룬다. `docs`로 정리된 docs·흩어진 Markdown·문서 없는 프로젝트의 현황과 비교/정리 후보를 조회한다. 검토한 실제 문서 변경안의 검사·적용·부분 실패·재개·복구를 CLI와 데스크톱에 연결했다. 실제 Codex·Claude의 스킬 발견과 요구 기반 자동 테스트를 확인했고, 실제 WebView2 앱에서 초기화·수집·문서/기록 조회·반영/복구·노트/작업/설정의 재시작 보존을 검증한다. Antigravity 앱 내 사용과 문서·분석의 최종 사용자 테스트는 남아 있으므로 전체 제품 완료로 표시하지 않는다.

개인 사용 경험을 먼저 검증하고 팀 계정·공유 권한·서버 동기화·Antigravity 연결·심화 일정 관리·검색/그래프 고도화는 후속 범위로 제안한다. 여러 PC 동기화가 초기 필수로 결정되면 이 순서와 저장 설계를 조정한다.

## 8. 검증과 관찰

### 구현 전에 준비할 요구 기반 사례

| 사례 | 기대하는 관찰 |
| --- | --- |
| 정리된 docs, 흩어진 Markdown, 채팅 중심 프로젝트 연결 | 수집 범위와 누락을 구별하고 원본과 프로젝트 귀속을 보존 |
| 같은 기록 재수집·초기화 재실행·다른 도구로 이어가기 | 중복 없이 같은 근거를 조회하며 공급자별 차이를 확인 |
| 시안을 탐색하며 반복 수정한 기록 분석 | 반복 작업과 기준 탐색을 지식 부족으로 단정하지 않고 근거·추정을 구별 |
| 공식·논문·커뮤니티 의견 충돌과 자료 접근 실패 | 출처·조건별 차이와 미확인 범위를 확인하고 후속 판단 가능 |
| 패턴 알림·마감 시각 변경·재실행·주간 집계 | 중복 알림·누락 기간·기간 경계를 구별하고 보고서와 연결 |
| 두 프로젝트에 규칙 적용 중 한쪽 외부 편집·실패 | 미선택 대상 보존, 충돌과 실제 반영 상태 확인, 재시도·복구 가능 |
| 사람 작업과 AI 실행이 겹치고 사용자 테스트 후 재작업 | 시간 합산 오류 없이 완료 판단·예상 변경 근거를 추적 |

개인 개발자는 여러 프로젝트의 분석에서 공통 규칙을 다듬고 선택한 프로젝트에 반영하는 흐름을 확인한다. 입문자는 자신의 요청 문맥에서 용어·요청 개선 가이드를 읽고 자유로운 추가 질문과 적용으로 이어가는 흐름을 확인한다. 두 경우 모두 화면·작업 순서는 바꿔서 검증한다.

초기 CLI 검증 명령은 `cargo test --all-targets --locked`이며 [테스트 사례 목록](../../tests/CASE_MATRIX.md)에서 구현·검증 범위와 남은 작업을 확인한다. SDK와 대조한 합성 자료와 기존 DB 자료로 이식 호환성을 확인한다. 새 동작은 요구 기반 실패를 먼저 확인한 뒤 구현·통합 검증한다. 마지막 제품 완료 판단에는 실제 Windows 환경에서 사용자가 직접 테스트한 결과를 포함한다. 문서 링크 검사나 CLI 테스트만으로 데스크톱·분석 경험까지 검증했다고 판단하지 않는다.

### 효과를 판단할 관찰 항목

- 분석·추천에서 사용자가 타당하다고 판단한 항목과 수정·제외한 이유.
- 기존 기록이 다음 작업에 재사용된 사례와 다시 조사하게 된 이유.
- 모호한 요청의 변화와 원하는 결과에 도달하기 위해 수정한 과정. 탐색 자체의 가치를 함께 해석한다.
- 규칙·문서 변경의 수동 정리 부담, 충돌·복구와 자발적인 반복 사용.
- 계획의 예상과 실제 차이, 비교 가능한 실적 수·조건·시간 기록의 완전성.

절감률·정확도·알림 탐지율·수용 시간 같은 목표 수치는 아직 측정 근거가 없어 설정하지 않는다. 기준선과 평가 자료를 확보한 뒤 조정한다.

## 10. 근거와 판단 경과
