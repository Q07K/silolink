# 버전과 커밋 규칙

- 기준일: 2026-11-09
- 상태: 0.4.0까지의 실제 방식을 정리하고, 정해지지 않았던 부분을 정했다.
- 관련: [배포 안내](releasing.md), [릴리스 노트](../../.github/release-notes.md), [버전 검사](../../scripts/release-version.ps1)

## 버전 번호

앱·CLI·프런트엔드·Codex 플러그인은 하나의 버전을 함께 쓴다. 형식은 [유의적 버전](https://semver.org/lang/ko/)의 `MAJOR.MINOR.PATCH`이고, 시험 배포만 `-rc.N`을 붙인다. 버전을 적는 파일과 일치 검사는 [배포 안내](releasing.md#릴리스-준비)에 있다.

1.0 전까지는 다음 기준으로 올린다.

| 올리는 자리 | 이럴 때 |
| --- | --- |
| MINOR (`0.4.0` → `0.5.0`) | 사용자에게 보이는 새 기능이나 동작 변경이 하나라도 들어갈 때. 저장 형식(`.silolink/`, 앱 데이터)·CLI 명령과 옵션·스킬 이름처럼 기존 사용자가 대응해야 하는 변경도 여기에 넣고 노트에 따로 적는다. |
| PATCH (`0.4.0` → `0.4.1`) | 버그 수정, 문구·색 같은 작은 다듬기, 배포 실패를 고쳐 다시 내는 경우. 새 기능은 넣지 않는다. |

여러 변경이 모이면 가장 큰 자리 하나만 올린다. 1.0의 시점은 따로 정한다. 1.0 이후에는 위에서 "기존 사용자가 대응해야 하는 변경"을 MAJOR로 올린다.

`X.Y.Z-rc.N`은 공개 전 설치·업데이트를 확인할 때만 쓴다. 하이픈이 들어간 태그는 GitHub에서 prerelease로 표시되고, 설치기는 `1.2.0-rc.1`을 `1.2.0`보다 낮은 버전으로 비교한다. 같은 내용을 정식으로 낼 때는 `-rc.N`을 뗀 버전으로 한 번 더 릴리스한다.

## 릴리스 커밋과 태그

1. 릴리스에 넣을 변경을 모두 `main`에 합친다.
2. `chore: release X.Y.Z` 커밋 하나를 만든다. 이 커밋은 버전 파일·lockfile·[릴리스 노트](../../.github/release-notes.md)만 바꾼다. 코드 수정은 앞선 커밋으로 따로 둔다.
3. 그 커밋에 주석 태그를 만들고 푸시한다. 메시지는 `SiloLink vX.Y.Z`로 통일한다.

```powershell
git tag -a vX.Y.Z -m "SiloLink vX.Y.Z"
git push origin main vX.Y.Z
```

푸시한 태그는 지우거나 다른 커밋으로 옮기지 않는다. 게시 job만 실패해 Release가 초안으로 남았다면 같은 태그로 워크플로를 다시 실행한다. 코드를 고쳐야 한다면 PATCH를 올려 새 태그를 만든다. 이미 공개한 Release는 워크플로가 덮어쓰지 않는다.

## 릴리스 노트

[릴리스 노트](../../.github/release-notes.md)는 새 버전의 `## X.Y.Z` 섹션을 맨 위에 추가한다. 공개한 버전의 섹션은 제목과 내용을 바꾸지 않는다. 태그만 만들고 공개하지 못한 버전은 그 섹션을 다음 버전으로 옮기고, 옮긴 섹션에 `X.Y.Z는 공개되지 않았다`는 줄을 남긴다.

항목은 사용자가 할 수 있게 된 일이나 달라진 점을 한국어 존댓말 한 문장으로 쓴다. 내부 리팩터링·테스트·CI 변경은 적지 않는다. PATCH에도 고친 증상을 사용자 관점에서 한 줄 이상 적는다. 저장 형식·CLI·스킬이 바뀌면 사용자가 할 일을 함께 적는다.

## 커밋 메시지와 브랜치

커밋 메시지는 [Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/) 형식의 영어 한 줄이다. 동사 원형으로 시작하고 끝에 마침표를 찍지 않는다.

| 타입 | 쓰는 곳 |
| --- | --- |
| `feat` | 사용자가 볼 수 있는 기능 추가·변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작이 같은 코드 정리 |
| `style` | 화면 모양만 바꾸는 변경 |
| `test` | 테스트만 바꾸는 변경 |
| `docs` | 문서만 바꾸는 변경 |
| `ci` | 워크플로·빌드 스크립트 |
| `chore` | 릴리스·설정·의존성 등 그 밖의 정리 |

범위는 바꾼 영역을 괄호로 붙인다. 루트 크레이트(`src/`)는 `core`, 앱(`desktop/`)은 `desktop`, 설치기는 `installer`, 워크플로는 `ci`를 쓴다. 여러 영역에 걸치면 범위를 생략한다. 예: `feat(desktop): edit the delegation phrase dictionary in settings`.

작업 브랜치는 `feat/…`, `fix/…`, `docs/…`처럼 주된 타입을 앞에 붙인다. AI 도구가 만든 브랜치는 `codex/…`, `claude/…`를 그대로 쓴다. `main`에는 병합 커밋으로 합치고 메시지는 `Merge <무엇을 합쳤는지>`로 쓴다.

## 알려진 한계

- v0.3.0 이전 버전(0.2.0 등)은 태그가 없다. 과거 커밋에 태그를 새로 달지 않는다.
- 게시 워크플로는 릴리스 노트 파일 전체를 Release 본문으로 쓴다. 그래서 각 Release에 이전 버전들의 노트도 함께 표시된다.
