# SiloLink — 새 프로젝트에서 이어갈 맥락

기준일: 2026-11-01. 이 문서는 대화의 인계용 정리이며 모든 제안을 구현 요구사항으로 확정하지 않는다.

## 확정한 내용과 지금 요청한 일

- 사용자가 **SiloLink(사일로링크)**라는 이름을 선택했다.
- 이름의 배경은 도구별로 분리된 정보 사일로를 연결한다는 것이다.
- 사용자는 폴더별 권한과 SSH를 분리해 GitHub를 관리한다고 설명했다.
- 레포 생성 요청은 이후 철회하고, 새 프로젝트에 전달할 맥락 정리만 요청했다.
- 현재 채팅에서 새 프로젝트 폴더·로컬 Git 레포·GitHub 원격 레포를 만들지 않았다. SSH·Git 원격·권한도 변경하지 않았다.
- 새 프로젝트의 위치·원격·기술 스택·최소 버전 범위는 미확정이다.

## 사용자가 설명한 문제와 장기 방향

업무와 사이드에서 기술 리서치를 반복하고, 그 결과를 기술 정리서로 공유하고 싶다. 처음에는 기술 블로그를 검토했지만 현재는 로컬 데스크톱 작업 공간을 먼저 생각하고 있다.

장기적으로 원하는 경험은 다음과 같다. 구현 순서나 첫 버전의 약속은 아니다.

- 정해진 리서치 폼으로 조사하고, 브레인스토밍도 같은 공간에서 수행한다.
- 조사 결과·아이디어·판단·개발 산출물을 프로젝트별로 묶는다.
- 관련 과거 문서를 추천하고 연결 이유를 볼 수 있다.
- 데스크톱에서 Claude Code·Codex·Antigravity 등 CLI를 이용해 작업한다.
- 반대로 외부 코딩 프로젝트에서도 SiloLink 자체 CLI·플러그인으로 기록을 저장·검색한다.
- 프로젝트를 한 번 연결하면 그 프로젝트에서 선택한 기록들이 모이는 경험을 원한다. 설치만으로 모든 기록의 완전한 자동 수집이 보장된다는 뜻은 아니다.
- 외부 에이전트에서 쓴 기록을 데스크톱에서 읽고, 데스크톱에서 정리한 기록을 다른 에이전트가 다음 작업에서 재사용한다.
- 사람이 읽고 공유할 수 있는 기술 정리서도 출력하고 싶다.

## 지금까지 확인한 사실과 한계

- 사용자는 기존 유사 도구를 **아직 사용해 보지 않았다**고 명시했다.
- 따라서 필요를 ‘기존 도구를 충분히 사용했지만 해결되지 않는 불편’으로 해석하면 안 된다.
- 세 CLI의 비대화형·구조화 출력 지원을 공식 문서와 이 PC의 도움말에서 확인했다. 실제 로그인·모델 호출·조사·취소·공급자별 호환성은 시험하지 않았다.
- GitHub·공식 제품 자료에서 주요 유사 후보 8개를 조사했다. 세부 내용과 한계는 [RESEARCH.md](RESEARCH.md)에 있다.
- 기존 제품의 완성도·실제 적합성·검색 정확도·시간 절약·유료 수요는 검증하지 않았다.
- SiloLink 이름의 상표·도메인·패키지 충돌도 확인하지 않았다.
- 앞선 에이전트의 별도 개발 권고는 비교 사용 전에 제시된 성급한 권고였다고 바로잡았다.

## 지금까지 나온 설계 제안 — 미확정

- 공통 기록 기능을 중심에 두고 데스크톱·자체 CLI·MCP·도구별 플러그인·외부 에이전트 실행 연결부를 나눈다.
- 데스크톱을 종료해도 CLI로 기록을 저장·조회할 수 있게 한다.
- 문서 원본은 Markdown·첨부파일 등 앱 밖에서도 읽을 수 있는 형태를 검토한다. DB·색인·저장 구조는 선택하지 않았다.
- 프로젝트 ID와 경로·워크트리·공급자 세션을 구분한다. 원본·출처·시각·버전·수정 이력·중복/동시 저장을 관리한다.
- 아이디어·제안·확정 결정·구현 결과·검증 결과를 섞지 않는다. 외부 자료의 주장과 직접 확인한 결과도 구분한다.
- 관련 문서 링크·태그·검색부터 시작한다. 본격적인 지식그래프가 과하다는 우려는 있었으나 제외 범위를 최종 확정한 것은 아니다.
- CLI 하나와 실제 작업 하나로 양방향 흐름을 검증한 뒤 확장한다.
- 선택한 산출물·명시적 기록부터 다루고, 훅 자동화·전체 세션 수집은 범위와 신뢰도를 별도로 판단한다.
- 원본은 유지하면서 관련 문서·후속 조사·다른 해결책의 연결을 제안한다. 단순 유사성으로 자동 병합하거나 최신 문서를 확정된 대체 판단으로 취급하지 않는 방향을 권고했다.
- 로컬 저장과 외부 모델 처리는 구분해야 한다. 현재 완전 오프라인 앱이나 무설정 자동화를 보장하지 않았다.

## 개발할 이유와 보류할 이유

개인 작업 절차에 맞춘 흐름·문서 검토와 공유·반복 사용·개발 학습에 가치는 있을 수 있다. 기존 제품의 기능 중복, 데이터 무결성, 공급자별 유지보수, 기록을 관리하는 부담과 외부 사용자의 전환 이유는 미해결이다.

개인 생산성, 개발 학습, 외부 사용자용 제품을 서로 다른 성공 기준으로 봐야 한다. 개발 착수·포기·기존 제품 채택 중 어느 것도 최종 결정하지 않았다.

## 새 프로젝트에서 먼저 정할 것

1. 우선 목적: 개인 생산성, 개발 학습, 외부 사용자용 제품 중 무엇을 우선하는가.
2. 실제 작업 한 건: 어떤 리서치/브레인스토밍 기록을 다음 코딩 세션에서 재사용할 것인가.
3. 기존 도구의 비교 체험 여부와 범위. The Vault·Basic Memory가 우선 후보라는 권고가 있었으나 사용자 의무나 확정 일정은 아니다.
4. 첫 버전의 포함·제외 범위와 완료 기준.
5. 대상 OS·우선 연결할 CLI·기존 문서 형식·데이터 저장/공유 범위.
6. 그다음 기술 스택과 구현 계획.

원래 대화 전체가 새 채팅에 자동으로 전달된다고 가정하지 않는다. 현재 새 프로젝트의 파일·지침·사용자 최신 요청을 함께 확인한다.
